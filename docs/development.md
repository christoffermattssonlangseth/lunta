# Lunta for developers

How Lunta is built: architecture, building from source, the Google Drive sync and its Google Cloud
setup, the desktop and Android apps, and the roadmap. For using Lunta, see the [README](../README.md).

## Architecture

```
core/                  Rust: library storage + sync layout, metadata lookup (Crossref, Europe PMC,
                       arXiv, OpenAlex), open-access PDF finder, annotations, full-text search
                       (SQLite FTS5), BibTeX/RIS import and export, citations, EPUB reading
core/src/convert/      Rust port of the paper → EPUB converter (DOI, PMCID, PubMed, arXiv, JATS XML,
                       PDF via PDFium) for future Linux/Windows/Android apps; features "convert" and
                       "pdf", not in the Apple build. CLI: cargo run --bin paper2epub -- <input> [out-dir]
core/src/drive/        Google Drive sync for devices without a synced folder (Android, Linux, ...):
                       RemoteStore trait, Drive REST client + OAuth (PKCE), Syncer; feature "drive",
                       not in the Apple build. CLI: cargo run --bin lunta-sync -- connect|sync|status
core/src/llm/          on-device AI for the desktop and Android apps: Qwen3 (GGUF) on llama.cpp, its download,
                       the Summary card's prompt and summary.json, Ask's retrieval; feature "llm", not in the
                       Apple build. Try it: cargo run --release --features llm --example ai
android/               Android app (Kotlin, Jetpack Compose, Material 3) on the core through UniFFI Kotlin bindings;
                       reader scripts reused from desktop/src/reader/generated/

                       TypeScript + Vite frontend (src/), reader scripts extracted from the Swift (src/reader/)

                       run time), its download; feature "tts", not in the Apple build (see Listen below)
```

### Library layout (sync-safe)

```
<library>/papers/<id>/paper.pdf     original PDF (if any)
<library>/papers/<id>/book.epub     reflowable version made by the converter
<library>/papers/<id>/fulltext.txt  plain text for search
<library>/ops/<device-id>.jsonl     append-only change log, one per device
<library>/positions/<device>.json   last reading position per paper (changes often, so not in the log;
                                    {paper: {offset, at (seconds since 2001), device}}, as Swift writes it)
<library>/smart-folders.json        smart folder rules
<library>/watches.json              watched authors, topics and citations
<library>/foryou.json               New for You: your interests, the feed, Add / More Like This / Not for Me feedback
```

Blobs are written once. Every change (metadata, read/starred, tags, collections, highlights and
notes) is an entry in the writing device's own log, so devices never write the same file and iCloud
never sees a conflict. Each device replays all logs (newest change wins) and keeps its own search
index in its cache folder.

### Reading: one paper, two views

Each paper keeps its **original PDF** and gains a **reflowable reading view** (the converted EPUB,
rendered in-app with WebKit). Both apps offer both views:

- iPhone: reading view by default (text reflows to the screen), PDF one tap away.
- Mac: PDF by default, reading view one tap away.

The reading view scrolls or turns pages (⋯ › Layout on iPhone, the book button or ⌥⌘P on the Mac).
Page mode cuts the page into screen-sized CSS columns (`apple/Shared/PageTurn.swift`); on iPhone the
web view's scroll view pages natively, so a page follows your finger. Contents, narration, highlights
and the synced reading position all turn to the right page.

There is no conversion back to PDF: the original PDF is kept, so nothing is lost. Highlights and
notes store the quoted text with a little context (`quote`, `prefix`, `suffix`) and a character offset,
so a highlight made on the phone finds the same words on the Mac whatever the screen width. Select text,
then **Highlight** / **Add Note** (right-click on the Mac, or ⇧⌘H; the edit menu on iPhone). Tap a
highlight to change its colour or note; *Highlights & Notes* lists them and copies them as Markdown.
A passage is found in the whole page's text, so one may run over paragraphs, a figure or (in pages on
iPhone and iPad) a page's end; it stays one highlight. In pages, a selection handle resting at the
screen's side, or with the selection's end at the end of the page's last line (its start at the
beginning of the first), turns the page (`luntaSelectionEdgeTurn`, one page per rest). The selection
can't follow (iOS WebKit re-anchors a handle drag at what is on screen), so it becomes a pending
Highlight to…: the passage stays coloured and the word tapped next ends it. Also without dragging: **Highlight to…** in the selection menu, or **Extend…** in a
highlight's sheet, then turn the page and tap the word where the highlight should end (before its
start: the start moves; inside it: it gets shorter); highlights it reaches are joined to it.

A figure's caption can be highlighted in the figure viewer too (Mac, iPhone, iPad, Windows, Linux,
Android): select words there for Highlight, Add Note or a colour (highlight mode: at once), tap a
highlight for its editor. It is the reading view's own highlight: the viewer's caption (title, a space,
caption; reference numbers and extra spaces left out) knows the page's text node and offset of each
of its characters (figureJS `capText`), so a passage selected there becomes the page's passage of
those words (`luntaFigures.select` → `luntaPassage`: quote, prefix, suffix and offset, with the chapter's
base in a book read chapter by chapter), exactly what selecting them in the reading view gives. It is
saved like any selection (merged with highlights it touches), so it shows in the text, *Highlights &
Notes*, outlines and summaries, and syncs. The viewer draws the marks the page has in the caption
(`luntaFigures.marks`: runs of the shown text with their ids), again after every redraw of the page's
highlights (`ReaderController.annotationsShown`). Captions of tables shown from a lone image (no figure
of the page) are only read and copied.

### Books and theses as PDFs

Before laying out a PDF, both converters decide whether it is a **paper** or a **book** (a thesis is
converted as a book): `DocumentClassifier` in `apple/Paper2EpubKit/Sources/Paper2EpubKit/DocumentKind.swift`,
`classify` in `core/src/convert/pdf/book.rs`. Anything under 40 pages is a paper (20 with a book or thesis
work type). Longer ones are scored on the page count, the PDF's outline (chapters with sections), an ISBN,
"Contents", "Preface", "Index" and "Chapter N" pages, dot-leader contents pages, running heads with page
numbers, and the work type the library knows (`Paper2Epub.knownType`, `Options::work_type`, `p2e --type`,
`paper2epub --type`); an abstract, a DOI line and received/accepted dates count against. A book needs a
score of 4. Papers go through the paper pipeline unchanged. In book mode (`PDFBookLayout.swift`, `book.rs`):

- chapters come from the outline (top level = chapter, second level = section in the contents, a part's
  chapters stay chapters), each entry placed where its title is printed (hyperref's `\chapter*` bookmarks
  point a page early) and titled as printed ("1.1 Supervised learning"); without an outline, from the
  headings found ("Chapter 3" over the title makes "3 Title");
- running heads and feet are the top and bottom lines that carry the printed page number (page index minus
  the book's offset) or repeat within four pages, so heads that change with the chapter go too;
- the printed table of contents (dot leaders, or the outline's "Contents" entry) is left out, the index is
  one chapter with an entry per line, and there is no abstract, affiliation or front-matter detection: the
  title page, copyright and dedication are a short "Front matter" chapter; authors come from the title page;
- numbered display equations ("… (2.2)") are cropped as images even when few of their glyphs are in a math font.

The decision and its signals are in the result (`ConversionResult.kind` / `kindReasons`; Rust `kind`,
`kind_reasons`), the log ("Document kind: book (+2 541 pages; …)"), a note in the book, and p2e's and
paper2epub's output. An app could give a library item converted as a book that has no work type yet the
type `book` (or `thesis`); the apps don't do that yet.

### Big reading views, chapter by chapter

A book's reading view (the 541-page "Understanding Deep Learning": 29 sections, ~190,000 words, 677
images, 50 MB of them) shown as one page went black on an iPhone: WebKit had to lay out (in pages, cut
into columns) the whole book, decoding its images, and iOS ended the page's web process for its memory.
Now (`apple/Shared/ChapterReader.swift`, `core/src/epub.rs`):

- **Images load lazily** in every reading view: `combine` (and the parts below) give each `<img>`
  `loading="lazy"`, `decoding="async"` and, where it has none, its pixel `width`/`height` from the file's
  header (the reader's CSS has `height: auto`, so the page keeps its layout while they load). The
  continuous view is marked `data-lunta-view="2"`; an older one is made again. Attributes add no text, so
  highlights and places are unchanged. (`content-visibility` was left out: it changes the geometry that
  restoring the place, Back, find and the page columns measure.)
- **Chapter by chapter** when `Library.readingParts` says so (`epub::chaptered`): at least 4 sections and
  60,000 words, 150 images or 30 MB of images (a long review paper has ~15,000 words and 10-40 figures).
  Sections become parts (`lunta-part-<n>.xhtml` next to the sections; short ones such as the title page,
  front matter and preface share one, until 1,000 words or 12 images), and the reader shows one part at a
  time, on the Mac and the iPhone alike. Papers (and anything below the thresholds) are shown as before.
- **Offsets stay those of the whole view.** A part's text is exactly a slice of the continuous view's
  text (the same `<body>` newline, `section-start` anchors and newlines), starting at its
  `<meta name="lunta-text-base">`. The page scripts add that base to every offset they give the app (a
  selection's `start`, `luntaPlace`) and take it off what they get (a highlight's `start`,
  `luntaHoldOffset`, `luntaMergeRange`), so highlights and reading positions are stored exactly as before:
  a highlight made in chapter 5 on the iPhone is found by the Mac, old highlights and saved places keep
  working, the MCP server's `add_highlight` (anchored in the continuous view's text) shows in the right
  chapter, and the place saved on one device opens its chapter on the other. The app gives the page the
  highlights of its part (`ChapterReader.split`: the part whose text has the quote, preferring the one the
  offset is in); one in no part is listed as not found.
- **Across chapters:** the contents and links (`lunta-part-3.xhtml#s30`, `ReaderNavigation`) open the
  chapter at the anchor; each part ends with "Next: …" and starts with "Previous: …" (empty links drawn by
  CSS, so no text); in pages, turning past the last page (tap, key, or on iPhone a swipe pulled past the
  end) opens the next chapter, before the first the previous one at its end. Find searches the whole book
  (`BookFind`: counted in the parts' texts, found and marked in the page of the part shown; Next past a
  part's last match opens the next part with one). Listen goes on into the next chapter (`Narrator.onEnd`;
  a narration rendered on the Mac for the whole book isn't used for these). Citations find their
  references in the reference list's part: the app hands its page to the others (`luntaSetShelf`, parsed
  with DOMParser, never part of the page), so the citation card and the References list work, and "Show in
  References" opens that chapter at the entry (`#lunta-ref-<n>`). The Summary card is left out (one
  chapter isn't the paper).
- **A web process that ends** (out of memory) is reloaded once (`webViewWebContentProcessDidTerminate`);
  if it ends again within 45 s the reader says "This reading view is too large to show at once on this
  device" with Show PDF and Try Again, instead of a black page.

Windows, Linux and Android get the lazy images (they show the continuous view the core makes); they
don't read books chapter by chapter yet.

### Web pages and blog posts

A link with no DOI, PubMed ID, PMCID or arXiv id in it (`webmeta::is_web_link`) is a web page: the
Add field on every platform, the browser extension's **Save as web page** (on a page with no paper on
it), Safari on iPhone/iPad (the inbox's `webpage` request) and the MCP server's `add_paper` all take
one. The core fetches the page once, as asked, with its HTTP agent and User-Agent
(`metadata::get_page`); the extension sends the page as the browser shows it instead (also what
scripts put in it). A page whose meta tags declare a DOI (`citation_doi`, Dublin Core, PRISM) is a
paper after all and is added by that DOI.

- **Details** (`core/src/webmeta.rs`), each field from the first source that has it: Highwire
  `citation_*` → Dublin Core → schema.org JSON-LD (BlogPosting / Article / NewsArticle / WebPage:
  headline, author, datePublished, publisher, isPartOf) → Open Graph and Twitter cards
  (og:title, article:author, article:published_time, og:site_name) → the page itself (`<title>`
  without its " | Site" tail, `<meta name="author">`, a byline: `rel="author"`, `itemprop="author"`,
  `.author`/`.byline`; `<time datetime>`; the site's name in its header or feed link) → a date in
  the address (`/2019/04/25/`). Authors are never made up: URLs, handles and "admin" are dropped; the
  one inference is a personal blog's owner, when the site is called "Andrej Karpathy blog" and the
  family name is in the host (karpathy.github.io). The address (without tracking parameters) and the
  day it was read (`PaperMeta.accessed`, UTC) are kept. Type: `post-weblog` for a JSON-LD BlogPosting,
  "blog" in the host, path or site name, a blogging platform (Medium, Substack, WordPress.com, Ghost,
  …) or a dated github.io address; `webpage` for anything else. The same address again is the same
  item (`Library::find_by_url`).
- **Reading view** (`core/src/webarticle.rs`, in every build: the Apple build gets the converter's
  HTML parser, `convert/html.rs` + `xml.rs`, and quick-xml for it): a readability-style reader, since
  the journal readers refuse a short page without sections. The main text is the `<article>` /
  `<main>` / `articleBody` / post container holding most of the page's text, else the element holding
  80 %; menus, headers, footers, sidebars, comments (Disqus), share/subscribe widgets and related posts
  are left out. Kept: headings (the top level starts a chapter), paragraphs, lists, code blocks
  (`<pre><code class="language-…">`, lines and indentation as they are, Rouge/Pygments line numbers
  out), blockquotes, tables, figures, MathML (KaTeX's MathML, MathJax's TeX), links (absolute) and
  footnote anchors. Images become `lunta-image:N`; they are fetched with the figures' rules (80 at
  most, 1600 px, SVG kept) by `convert::webpage::web_book` (Rust: desktop, Android, MCP) or
  Paper2EpubKit's `Paper2Epub.convert(webPage:…)` (Apple: the core reads the page through UniFFI,
  `fetchWebPage` / `readWebPage`, Swift fetches the images and writes the book). Fewer than 60 words:
  no reading view, the details are saved with a note.
- **Citing:** the built-in styles have their own web forms (`export::web_citation`), e.g. APA
  "Karpathy, A. (2019, April 25). A Recipe for Training Neural Networks. Andrej Karpathy blog.
  https://karpathy.github.io/2019/04/25/recipe/" (a web page's title in italics, a blog post's not;
  no date: "(n.d.) … Retrieved November 21, 2026, from URL"); MLA, Harvard, AMA, IEEE, Vancouver and
  ACS give the access date. CSL (hayagriva): type `webpage` / `post-weblog`, the site as
  `container-title`, `URL` and `accessed`. RIS: `ELEC` / `BLOG` with `Y2` (accessed). BibTeX:
  `@misc` with `howpublished = {Site, \url{…}}` and `note = {Accessed …}` (what plain/unsrt/natbib
  styles print) plus `url`, `date` and `urldate` (what biblatex prints); biblatex users see the address
  and date twice unless they drop the first two. Imports read all of these back; a folder's .bib keeps
  web pages as its extra entries, as before. In Word and Google Docs, Zotero's "Web Page" and "Blog
  Post" items keep their type and access date when converted (`cslMeta` in apple/citations/common.js).

## AI agents (MCP)

Lunta ships an [MCP](https://modelcontextprotocol.io) server, `lunta-mcp`, inside the Mac app, so AI agents can work with
your library: Claude Code, Claude Desktop, Cursor or any MCP client. Connect one with **Lunta › Connect AI Agents…**, or by hand:

```sh
claude mcp add --scope user lunta -- /Applications/Lunta.app/Contents/MacOS/lunta-mcp
```

Tools: `search_papers`, `list_papers`, `get_paper`, `read_paper` (full text, or the passages matching a query), `cite`
(APA, Vancouver, Nature, …, BibTeX with the fixed keys, `latex` for `\cite{…}`, RIS), `library_overview`, `find_new_papers` (OpenAlex), `add_paper` (also a web page or blog post by its link), `find_pdf`,
`tag_papers`, `add_to_collection`, `set_status`, `add_note`, `update_paper`, `resolve_citations` (the placeholders in a text the
user is writing, "(Smith et al. 2019)" or `\cite{?smith2019}`, each with up to five candidate papers; read-only, see Resolve Citations), `check_references` (a reference list checked against the published record) and `library_status` (papers flagged retracted or corrected, preprints since published; both read-only, see Checks against the published record), `outline_from_highlights` (a Markdown outline of the highlights in some papers, read-only), and for highlights `list_highlights` (across the library; filter by paper, colour, tag, collection or words), `add_highlight` (quote a passage; it shows in the reading view and the PDF) and `update_highlight` (note, colour, delete).

The agent writes through its own change log (`ops/agent-….jsonl`), exactly like another device, so it can work while the
apps are open and its changes sync to the Mac and iPhone. The same binary is a command-line tool:

```sh
lunta search csf lactate
lunta read <id> "how many patients"
lunta cite <id> <id> --style vancouver
lunta path <id> pdf
```

Inside the apps, **Ask** (✨) runs a small agent on the device with the same kind of tools: Apple's
on-device model, or Qwen3 4B (4-bit, via MLX; a one-time 2.3 GB download) when Apple Intelligence is off
or unavailable. Pick the model in the panel's ⋯ menu.

The apps deploy to macOS 15 and iOS 18. FoundationModels only exists from macOS/iOS 26, so it is
weak-linked (`-weak_framework FoundationModels` in project.yml) and every use is behind
`#available(macOS 26.0, iOS 26.0, *)`; the open model plugs into FoundationModels' `LanguageModel`
protocol, which needs macOS/iOS 27. Before 26, `AskEngine.unavailableReason` says the assistant needs a
newer system, `plainAnswer` returns nil (New for You ranks without screening or summaries, Tidy and
Outline keep their model-free grouping), there is no Summary card and "Read Title and Authors from the
PDF" is off. SwiftUI modifiers new in 26 go through `Shared/Compat.swift`.

## Citations in Word and Google Docs

**Lunta › Citations in Word & Google Docs…** sets them up (Windows and Linux: **Settings ▾ › Citations in Word &
Google Docs…**, see [Word on Windows and Linux](#word-on-windows-and-linux)). Both talk to the app over
`https://localhost:47481` (a certificate made for this computer only; trusting it needs your password once on the
Mac, a Yes on Windows).

- **Word:** *Install in Word*, restart Word, then **Cite** on the Home tab. Search, pick papers, *Insert
  Citation*; *Insert Bibliography* where the references go; *Update All* after edits or a style change.
  Citations are content controls tagged with the paper ids, so they survive editing and renumber.
- **Google Docs:** with the browser extension (1.1+), the **Lunta** button on any document (see below); or,
  without it (Safari), Extensions › Apps Script; paste `Code.gs` and an HTML file `Sidebar` (both copied from
  the Lunta window; the sidebar carries a pairing key), reload, then **Lunta › Cite…**.

Styles: APA 7, Harvard, Chicago (author-date), Cell, MLA 9, Vancouver, IEEE, AMA, Nature, Science, PNAS and ACS, and any of the ~10,000 journal styles of the [Citation Style Language](https://citationstyles.org) catalogue (*Find journal style…*: fetched once from zotero.org/styles, formatted in the core with [hayagriva](https://github.com/typst/hayagriva)). Lunta must be open to search and cite.

How it fits together:

- `apple/citations/common.js` does the numbering and formatting for both add-ins (numbers by first
  citation, ranges, a/b for the same authors and year, the reference list exactly the cited papers);
  `word/app.js` and `gdocs/Code.gs` + `Sidebar.html` only read and write documents.
- `CitationAPI` (in `apple/LuntaCore/Sources/LuntaCore`, next to the generated bindings so the package
  tests reach it) answers the add-ins and decides who may ask: pages from Lunta itself, the hosted Word
  panel, and the Google sidebar with the pairing key; requests from other web pages are refused, also
  those a browser sends without an Origin (`Sec-Fetch-Site`), and so is any other `Host` (DNS rebinding).
  `CitationCertificates` makes the certificate authority (name-constrained to localhost and 127.0.0.1, so
  its key can be kept) and renews the localhost certificate a month before its 820 days run out, without
  trusting anything again. `apple/Mac/CitationServer.swift` is the socket and TLS around them.
- **Documents carry their papers.** Word keeps the style and a copy of each cited paper's details (and
  its entry in the current style) in a custom XML part (`https://lunta.app/ns/word-citations/1`; add-in
  settings would be per add-in id, and the sideloaded and store manifests differ); Google Docs keeps them
  gzipped in document properties (`lunta.store.*`) and, since `Code.gs` version 3, in named ranges
  (`lunta:<generation>:<i>:<n>:<base64url>`, which the browser extension reads and writes too). Lunta formats a paper it doesn't have from these
  details, or finds it again by DOI or title (a merged duplicate, another library); with Lunta closed,
  Update All works from the saved entries. A cited paper with nothing to go on stops Update All with the
  citation selected; nothing is written.
- Update All writes only what changed (so twice changes nothing, and Track Changes shows only real
  changes). Google Docs checks the document still has the citations the update was worked out for and
  starts over if someone typed meanwhile, finds citations in footnotes and in every tab, and keeps the
  bibliography's paragraph formatting. Older `Sidebar.html` copies keep working with the new `Code.gs`
  (`applyAll`); a new sidebar asks for both files to be copied again when `Code.gs` is older.

Tests: `node --test apple/citations-tests/` (the shared formatting, `Code.gs` against a stand-in for
Apps Script's DocumentApp, and the extension's Google Docs code against a stand-in for the Docs REST API, also
as Lunta for Mac runs it for Safari: `gdocs-safari.test.js`, and `gdocs-safari-swift.test.js`, which compiles
`GoogleDocsScript.swift` with a test driver), `swift test --filter CitationAPITests` in `apple/LuntaCore` (the API on a
scratch library, the access rules, certificates), and the citation tests in `core` (`cargo test cit`).
What only Word and Google Docs can show is in [citations-testing.md](citations-testing.md).

### Word on Windows and Linux

At KI most people write in Word on Windows, so Lunta for Windows serves the same add-in as the Mac: the same
`manifest.xml` (sideloaded) and `manifest-store.xml` (the store, panel from getlunta.app) work unchanged.

- **Server** (`desktop/src-tauri/src/citeserver.rs`): HTTPS on 127.0.0.1:47481 with rustls (ring, as the updater
  already has it), a thread per connection, idle connections closed after 30 s, the port retried for a while if
  taken. It serves `apple/citations` at the Mac's paths (`/word/index.html`, `/common.js`, `/icons/…`), compiled
  into the app with `include_bytes!` (no resource paths to get wrong between the MSI, NSIS, AppImage and dev
  runs; a test fails when a file in `apple/citations` is missing from the list), and `/api/…` as the extension's
  `/cite/…` in `citeapi.rs` (one implementation of the routes for both). The access rules are
  `CitationAPI.refusal` / `corsHeaders` ported rule for rule (`Access`), with the hosted panel at both
  `https://getlunta.app` and the earlier GitHub Pages origin. On a Mac it stays off (Lunta for Mac has the port;
  `LUNTA_CITATION_PORT` in debug builds).
- **Certificates** (`citecerts.rs`, rcgen): `CitationCertificates`' scheme. An authority (ECDSA P-256, 10 years,
  `pathlen:0`, critical name constraints: DNS `localhost`, IP `127.0.0.1/32`) and a localhost certificate it
  signs (820 days, serverAuth, SANs `localhost` and `127.0.0.1`), renewed a month before it runs out, checked
  daily while the app runs and swapped into the server without a restart; a new authority only when its key is
  gone or damaged or the next certificate would outlive it. In `<app data>/citations/tls`; the keys are DPAPI-
  protected on Windows (`CryptProtectData`, this user only), 0600 in a 0700 folder elsewhere.
- **Setup** (`citesetup.rs`, the window in `desktop/src/citations.ts`):
  - *Trust, Windows*: `CertAddEncodedCertificateToStore` into `CERT_SYSTEM_STORE_CURRENT_USER` `Root`. No
    administrator; Windows itself shows "Security Warning: You are about to install a certificate from a
    certification authority (CA) claiming to represent: Lunta Local CA (this computer only, localhost)… Do you want
    to install this certificate?" (Yes / No; No is reported as such). Word (WebView2), Edge and Chrome use that
    store. This is the store `office-addin-dev-certs` uses for Office's own add-in development. Trusted = the
    authority's bytes are in the user's Root view (which includes the machine's).
  - *Trust, Linux*: browsers keep their own NSS databases. With `certutil` (libnss3-tools / nss-tools) Lunta adds
    the authority (`-t C,,`, nickname "Lunta Local CA") to `~/.pki/nssdb` (Chrome, Chromium; made if missing)
    and every Firefox profile (also Snap, Flatpak and ~/.config/mozilla/firefox); without it the window explains the import in each browser's
    settings and saves `ca.pem`.
  - *Install in Word* (Windows): the manifest goes to `<app data>/citations/manifest.xml` and is registered as
    `HKCU\Software\Microsoft\Office\16.0\WEF\Developer`, value `6a1f3b2c-…` (the add-in's id) = the
    manifest's path: what `office-addin-dev-settings sideload` does, per user, no administrator. Word 2016, 2019,
    2021, 2024 and Microsoft 365 read it at start; Cite appears on the Home tab (and under Developer Add-ins).
    Rejected: a shared-folder catalog (`WEF\TrustedCatalogs`) needs a UNC share, which needs an administrator
    to create; the store listing (when it's there) needs no installing at all.
  - *Word on the web*: Save Manifest…, then Home › Add-ins › More Settings › Upload My Add-in (kept by that
    browser).
  - *Remove*: the registry value, the authority from the user's Root store (Windows asks again) or the NSS
    databases, and the certificate files; a new authority is made at once, so no key remains that a trusted
    certificate came from.
  - Status: serving or why not, trusted, installed, and "Word is connected" when an add-in asked in the last
    ten minutes.
- **Limits.** Not tried on a real Windows PC yet (see [citations-testing.md](citations-testing.md)): the trust

### A paper's options in a citation: page, prefix, suffix, author

As in Zotero's citation dialog, each paper in a citation can have a **locator** (a CSL locator type, page by
default, and its number: "p. 12", "chaps. 3–5", "fig. 7"), a **prefix** ("see"), a **suffix** ("for a review")
and an author **mode**: as the style has it, *suppress* (without the author, "(2024)", for when the name is in
the sentence already) or *narrative* (the author in the text: "Kukanja et al. (2024)"). Click a citation; each
paper has **Page…** (Word panel, extension panel; the Apps Script sidebar's **Edit Citation at Cursor**), a form
built by `LuntaCite.optionsForm` (kind of locator, number, prefix, suffix, author; Enter applies, Escape closes).

- **Stored outside the paper ids**, so add-ins from before still read the citation: in Word in the content
  control's **title**, `Citation lunta-o:<code>` (the tag stays `margins:<ids>`); in Google Docs in **named
  ranges over the citation's text**, `lunta-o:<key>:<i>:<n>:<part>` (Docs names are 256 characters at most;
  the parts put together in order). The code is base64url of the JSON with short keys (`p`, `s`, `l`, `t`, `m`),
  written and read by `common.js` (`encodeOptions`, `optionsTitle`, `optionRangeNames`, `optionsCodeOf`; the
  extension's `docs-model.js` reads the names itself, a test checks they agree). Update All re-creates a
  citation's ranges over its new text (the extension deletes them by id first; `Code.gs` re-adds them).
- **Older add-ins** with a newer document: Word's (before 13) read the papers from the tag, format the citation
  without its options and leave the title, so a newer panel puts them back at the next Update All. Google Docs'
  (`Code.gs` 3, and the extension as released before this change) don't see the ranges; when they rewrite a citation's text, Docs drops the
  ranges with the old text and that citation's options are lost (its papers aren't). `Sidebar.html` 4 asks for
  `Code.gs` 4.
- **Formatting.** Built-in styles in `common.js` `format(style, citations, entries, store, options)`: author–date
  "(see Smith, 2020, p. 12)", Chicago and MLA without "p." ("(Smith 2020, 12)", "(Smith 12)"), works with
  options not merged into "Smith, 2020a, 2020b"; numbered "[see 1, p. 12]", "[1–3; 4, p. 2]" (ranges only
  between plain numbers), superscript "1(p12)"; *narrative* "Smith (2020, p. 12)", or "Smith [3]" in a numbered
  style (that citation isn't raised: `superscripts`). Journal styles: `/render` takes `options` (one per citation,
  `{id: {locator, label, prefix, suffix, mode}}`); the core (`csl::render_items`, `Library::cite_csl_items`)
  gives hayagriva each paper's `SpecificLocator` and, for *narrative*, `CitePurpose::Prose`; the prefix and
  suffix go around the paper's part of the engine's output (marked `ElemMeta::Entry`), and *suppress* takes the
  first names element out of it (hayagriva has no per-item affixes, and its `CitePurpose::Year` drops the
  citation's brackets and year suffixes).
- **Superscript citations.** The words the writer adds stay on the line: in a raised citation the first
  paper's prefix and the last one's suffix aren't raised ("see ⁴", "⁴ for a review"; a prefix or suffix of a
  paper in the middle stays raised with its number). The core says which start and end of the text aren't
  raised (`CslCitation::before`, `after`; /render's `citations: [{text, superscript, before, after}]`),
  `format` does the same for the built-in Nature, AMA and ACS, and the panels get them as `befores` and
  `afters`; the Word panel writes the raised middle and then the plain start and end (Google Docs still
  raises the whole citation). Many superscript journal styles (Cell and the Cell Press journals, Nature)
  print no locators at all, so a page given there was lost: for a style whose XML names no `locator`
  variable, the core adds each paper's locator after its number as the built-in superscript styles write
  it ("⁴⁽ᵖ⁵⁾", "[4, p. 5]" when not raised), English labels, and such a citation isn't collapsed into a range
  ("1(p1),2,3", not "1(p1)–3"). A style with its own locator rule prints it as it says.
- **The bibliography in Word** is HTML put into its content control; Word gives the HTML's paragraphs its
  own font and spacing but keeps the control's last paragraph mark with whatever was there (another
  manager's bibliography, the theme's font), so the last entry came out in another font. After writing it,
  every entry gets the first entry's paragraph spacing and indents and the font (name, size, colour) of the
  paragraph the first citation is in (`evenBibliography`).

### Converting citations from Zotero, EndNote and Mendeley

Researchers bring manuscripts written with other reference managers. **Convert Citations from Zotero, EndNote or
Mendeley…** (Word panel) and **Convert Citations from Zotero…** (Google Docs: the extension and the Apps Script
sidebar) read the other manager's citations, find their papers, show a review ("12 citations, 34 papers: 30 in
your library, 4 to add", the papers to add with a tick each, what can't be read), and change nothing until
**Convert**. Then the papers ticked are added (`/add`), every citation whose papers are all in the library
becomes a Lunta citation with the options the manager kept, the manager's bibliography becomes Lunta's (or goes,
if there is one already) once none of its citations is left, and Update All formats everything in the document's
style. A citation with a paper not found or not added stays exactly as it was and is listed afterwards.

- **What is read** (`word/fields.js` for Word, `common.js` for the shared parts):
  - Zotero in Word: fields `ADDIN ZOTERO_ITEM CSL_CITATION {CSL citation JSON}` (the JSON right after
    `CSL_CITATION`, possibly with text after it, so the object is taken by brace matching), bibliography
    `ADDIN ZOTERO_BIBL {…} CSL_BIBLIOGRAPHY`. Items: `itemData` (CSL-JSON: title, author with particles or
    `literal`, `issued` date-parts / raw, container-title, DOI, PMID…), `locator`, `label`, `prefix`, `suffix`,
    `suppress-author`, `author-only` (as narrative). "Store citations as bookmarks" documents (bookmarks
    `ZOTERO_BREF_…`, the codes in document properties) aren't read: the panel says to switch Zotero to fields.
  - Mendeley Desktop: `ADDIN CSL_CITATION {…}` (older: `ADDIN Mendeley Citation{uuid} CSL_CITATION`, a
    `mendeley` object), bibliography `ADDIN Mendeley Bibliography CSL_BIBLIOGRAPHY`. Mendeley Cite: content
    controls tagged `MENDELEY_CITATION_v3_<base64 JSON>` (same CSL items), bibliography `MENDELEY_BIBLIOGRAPHY`.
  - EndNote: `ADDIN EN.CITE <EndNote><Cite>…<record>…</record></Cite></EndNote>` in the field code, or (long
    citations) the same XML base64 in the field's `<w:fldData>` with an `ADDIN EN.CITE.DATA` field nested inside
    (UTF-8, or UTF-16 if it looks so). `<record>`: titles (EndNote's `<style>` wrappers dropped), authors
    "Family, Given", year, secondary-title / periodical, volume, number, pages, `electronic-resource-num`
    (the DOI in it), `accession-num` (a PubMed id when it is one), urls. `<Cite>`: `<Prefix>`, `<Suffix>`
    (EndNote's "`" for a kept space), `<Pages>` (the cited pages, only before `<record>`, whose `<pages>` are the
    article's), `ExcludeAuth="1"` (suppress), `AuthorYear="1"` (narrative). Bibliography `ADDIN EN.REFLIST`.
    Unformatted temporary citations ("{Smith, 2020 #12}") aren't read (Resolve Citations can take them).
  - Zotero in Google Docs: text linked to `https://www.zotero.org/google-docs/?<key>` (6 characters), the code in
    named ranges `Z_F<key><000…><part>` ("ITEM CSL_CITATION {…}"; "BIBL …" for the bibliography, whose
    paragraphs are linked to its key), as zotero-google-docs-integration writes them. Paperpile's links
    (`paperpile.com/c/…`) are counted and reported: their details are on Paperpile's server. Mendeley and
    EndNote have no Google Docs citations to read.
- **Finding the papers**: `POST /match {items: [meta]}` (API 4; `Library::match_cited_papers`,
  `core/src/citeimport.rs`): DOI, PubMed id, the same title (with years at most one apart), or the same first
  author, year and nearly the same title (shared words ≥ 0.8, and the same numbers, digits or roman numerals, so
  Part I and Part II or Phase 2 and Phase 3 stay apart; `how: "close"`, listed in the review to be unticked, which
  adds the work as a paper of its own). Works are taken once (by DOI, else title and
  year) across citations.
- **Writing, Word**: the document's OOXML (`body.getOoxml()`) is read for the fields (instructions split over
  runs and paragraphs, entities, `fldData`, nesting); Word's own `body.fields` come in the same order and are
  matched by their code (`LuntaFields.sameCode`); a field is replaced by selecting it (`Field.select`, WordApi
  1.5) and inserting a Lunta citation (content control) in its place, so the text around it keeps its
  formatting; the last first. Mendeley Cite's controls just get Lunta's tag and title. Word has no undo group
  for add-ins: the review says to keep a copy. Needs WordApi 1.5 (Word 2021, Microsoft 365, Word on the web) for
  fields; citations in footnotes aren't read (`body` only).
- **Writing, Google Docs**: one `batchUpdate` for the revision read (extension `flow.js` `convertZotero`,
  `docs-model.js` `zoteroRequests`; `Code.gs` `zoteroConvert`): the citation's text relinked to
  `margins.local/cite?ids=…` with its options' ranges, the bibliography's paragraphs relinked to
  `margins.local/bib` (or deleted), the converted keys' `Z_F` ranges deleted; then Update All. The version
  history keeps the document as it was.

Tests: `node --test apple/citations-tests/` (`fixtures-word.js`: Zotero with its code split over three runs and a
title with `<&>`, EndNote inline and as `fldData` with a nested field, Mendeley Desktop and Mendeley Cite, a
`HYPERLINK` field between them, the bibliographies; Zotero in Google Docs for the extension and `Code.gs`),

`swift test --filter CitationAPITests`. Real documents: see citations-testing.md.

### Resolve Citations: write first, cite later

Writers type placeholders while writing and let Lunta turn them into citations, **confirming each one**: Lunta
proposes, the writer decides. Nothing is written into a document or added to the library without that.

- **What is a placeholder** (`core/src/placeholders`, `find_placeholders`): "(Langseth et al. 2025)",
  "(Langseth et al., 2025; Smith 2019)", "[Langseth 2025 spatial]" (words after the year are hints), "{Langseth
  2025}"; family names with accents, hyphens, particles ("van der Berg"), "O'Brien", "and" / "&", "et al.", a year
  1800–2100 with a letter ("2019a"), "Smith 2019, 2020" as two works, a "see" / "e.g." in front. Every part
  between the brackets must be names and a year, so "(see Fig. 2)", "(n = 2025)", "(p < 0.05)", "(2019–2020)",
  "(Table 1)", "(January 2020)", "[1-3]", a Markdown link or a sentence in brackets are not. LaTeX
  (`find_tex_placeholders`): `\cite{?key}` / `\cite{key?}` in any `\cite…` command (options and the other keys
  kept; the key read as name, year and hints: `?langseth2025spatial`), and the "(…)" and "[…]" forms ("{…}" is
  LaTeX's), not in comments. Offsets are UTF-16 (JavaScript, Word, Google Docs, NSString). Not recognised:
  narrative citations ("Langseth et al. (2025)"), placeholders without a year (except LaTeX keys), names in
  scripts without capitals.
- **Candidates** (`Library::suggest_citation`, up to 5): the library's first, scored by the first family name
  (first author 0.5, another author 0.15), the other names, "et al." against the number of authors, the year
  (exact +0.35, one off +0.1 for online-first and preprints, otherwise −0.3) and the hint words (in the title,
  else journal, keywords, abstract); a LaTeX key that is a paper's own key is certain. **Exact** when exactly one
  library paper has the first author, the year and every hint word: only those may be confirmed together
  (Confirm All Exact Matches). Without an exact match, Crossref (`query.author` with the names, the hints, the
  years around), or OpenAlex when Crossref has nothing; a work the library has (DOI or title) shows as the
  library's. `search_citation` is the panels' Search; `add_found_paper` adds a confirmed outside paper (its record
  from the DOI).
- **The citation API** (version 3, now 4; `CitationAPI.swift`, `desktop/src-tauri/src/citeapi.rs`): `POST
  placeholders {texts, latex?}`, `POST suggest {cite} | {query}`, `POST add {meta}` (the app then shows the paper
  and looks for its PDF).
- **Word and Google Docs** share `apple/citations/resolve.js` (the extension's `gdocs/citations-resolve.js` is a
  copy; a test checks): the list, Confirm / Skip / Search… per part, and writing a placeholder once all its parts
  are decided (outside papers added first, the parts skipped left as written after the citation, then Update
  All). Word scans the paragraphs' text and finds each placeholder with Word's search outside content controls
  (Lunta's citations), the n-th of the same text, and makes it a citation as Insert Citation does. Google Docs:
  `LuntaDocs.plainSegments` (plain runs in every tab, table and footnote, split at any link, footnote mark or
  image), `flow.js` `scanPlaceholders` / `writePlaceholder` (found again where it is now, one `batchUpdate` for the
  revision read, "(…)" linked as a citation, then Update All); in Safari Lunta for Mac runs them.
- **LaTeX** (Mac `apple/Mac/TexResolve.swift`; Windows and Linux `src/texresolve.ts`, `src-tauri/src/texresolve.rs`):
  Resolve Citations in a .tex File… lists the placeholders; on Write the outside papers are added, every confirmed
  paper goes into the chosen folder (the one whose .bib is kept), `rewrite_tex_placeholders` writes the keys,
  the original stays as `.tex.bak`, and the kept .bib is rewritten.
- **Limits.** The Apps Script sidebar has no Resolve Citations; Word only looks in the main text (not footnotes);
  Crossref without hint words returns the author's papers by relevance, so a common name needs a hint or a
  Search; a placeholder edited between the scan and the confirmation is found again by its text (Docs: nearest
  to where it was) or reported.

Tests: `cargo test placeholders` in `core` (recognised and not, LaTeX rewriting, ranking on a temporary library,
recorded Crossref and OpenAlex answers), `cargo test resolve_citations` and `cargo test texresolve` in
`desktop/src-tauri`, `swift test --filter CitationAPITests`, and the Word, Google Docs and Safari flows in
`node --test apple/citations-tests/`.

### Citing in Google Docs from the browser extension

Pasting Apps Script into every document (and pairing it) is too much to ask; Zotero and ReadCube cite from
their browser extensions. Lunta's does the same (`extension/gdocs/`):

- **How it reads and writes.** Docs draws its pages on a canvas, so the page's DOM can't be edited. The
  extension uses the **Google Docs REST API** (`documents.get` with tabs, `documents.batchUpdate`), signed in with
  `identity.launchWebAuthFlow` (Chrome, Edge, Firefox; one *Web application* OAuth client, scope `documents`; the
  token only in the background script, in session storage). This is what Zotero does.
- **Where the cursor is.** The API doesn't know. The panel pastes a placeholder through Docs' own paste handling
  (a synthetic `paste` on Docs' input iframe, `.docs-texteventtarget-iframe`, as Zotero does): a link to
  `https://margins.local/insert?t=<token>&ids=…` (or `&bib=1`). The background then finds it with the API (Docs
  saves within a second or two; it polls up to 15 s) and makes it the citation in the same Update All: pasted
  inside a citation (Docs splits that link around it) the papers join it; a bibliography placeholder becomes new
  paragraphs after its paragraph (plain body text, no list). A selection is collapsed to its end first (Docs puts
  the selection in its input on a synthetic `copy`), so nothing is replaced. A placeholder left behind isn't a
  citation to the Apps Script and becomes one at the next Update All.
- **Writing.** `docs-model.js` turns the document into the citations in order (tabs, footnotes where their
  marks are, tables; runs split by formatting joined) and the bibliography paragraphs, and makes the requests:
  new text inserted after the old, the old deleted, then styled (link, no underline, superscript or not), from the
  end of each part to its start so positions hold; the bibliography's new text goes in before the old so its
  paragraphs keep their look (lists, indents), and its last paragraph mark is never deleted. One `batchUpdate`
  with `writeControl.requiredRevisionId`: if anyone typed since it was read, Google refuses it whole and the
  extension starts over (three times). Text that's already right isn't written (Update All twice changes nothing).
- **Formatting** is the add-ins' own: `gdocs/citations-common.js` is a copy of `apple/citations/common.js`
  (a test fails when they differ: copy it after changing common.js), with Lunta's answers from the extension
  endpoint's `/cite/…` routes, which are the citation API's (`CitationAPI.answerTrusted` on the Mac;
  `desktop/src-tauri/src/citeapi.rs` on Windows and Linux). The endpoint already accepts only the extension, so
  no certificate to trust and no pairing key.
- **The same documents as the Apps Script.** Same citation and bibliography links; the style and the cited
  papers in named ranges over the first tab's text, which both read and write (document properties are visible
  only to the script that wrote them). A document whose style isn't in it (written with `Code.gs` 2) has its
  citations left alone until the user picks the style.
- **Rejected:** editing through the page (canvas; Docs' accessibility DOM is read-only and changes often);
  reading through `export?format=html` and writing by paste only (no way to rewrite existing citations or the
  bibliography: Update All and style changes are the point); `chrome.identity.getAuthToken` (Chrome only; a second
  OAuth client); the narrower `drive.file` scope (needs the Google Picker per document, a remote script an MV3
  extension can't load: see google-docs-extension.md); keeping only the Apps Script (it stays, as the fallback); for Safari, a second
  implementation of the citations in Swift (the app runs the extension's JavaScript instead), and
  `ASWebAuthenticationSession` (it doesn't take a loopback redirect, which a Desktop client needs).
- **Safari (on the Mac): Lunta for Mac does the Google part.** Safari has no `identity` API for extensions and
  blocks the synthetic paste. There, the background script passes the panel's requests (status, connect,
  disconnect, state, update, prepareInsert, finishInsert, details, editCitation) to the app, `POST /gdocs` on
  the extension endpoint (searching and styles keep using `/cite/…`). The app signs in to Google as an
  installed app (`GoogleDocsAuth.swift`: a *Desktop app* OAuth client, Google's page in the default browser, PKCE,
  a loopback redirect to `http://127.0.0.1:<free port>` it answers itself; the refresh token in the Keychain) and
  answers with **the extension's own code**: `GoogleDocsScript.swift` loads `citations-common.js`,
  `docs-model.js`, `flow.js` and `app-host.js` from the Safari extension inside the app into a JavaScriptCore
  context; what JavaScriptCore lacks (the Docs API with the app's token, the citation API, gzip, waiting) is
  bridged to Swift. So there is one implementation of the citations for every browser; the requests the panel
  makes are `flow.op`, answered by the background script in Chrome and Firefox and by the app in Safari.
  Inserting: Insert Citation / Insert Bibliography put the placeholder (the same linked `(…)`) on the clipboard
  from the click itself (`navigator.clipboard.write` with `text/html` and `text/plain`; Safari takes the
  app's answer as a promise in the `ClipboardItem`, `gdocs/clipboard.js`), the panel says "Press ⌘V in the
  document where the citation goes" and asks the app (`finishInsert`, 4 s at a time, up to 3 minutes, Cancel)
  until it has arrived. Pasted as plain text (⌘⇧V, or the link dropped): one more unlinked `(…)` than when it
  was copied; the panel says to undo and paste with ⌘V, and keeps waiting. Clicking a citation to edit it works
  as in the other browsers (the link bubble is in the page). Safari on iPhone and iPad: no app nearby; the panel
  points to the Apps Script.
- **Limits.** Safari needs Lunta for Mac open, and its own OAuth client (empty until made:
  `GoogleDocsClient` in `GoogleDocsAuth.swift`, see google-docs-extension.md), and the reader's ⌘V. Google's verification of the `documents` scope is needed before more than 100 people can sign in.
  The paste and copy tricks depend on Docs' page; if Google changes it, inserting fails with a message (Update All,
  through the API alone, keeps working).

What you set up in Google Cloud (the OAuth client, the consent screen, verification) is in
[google-docs-extension.md](google-docs-extension.md); the client ID goes in `extension/gdocs/config.js`.

## LaTeX: citation keys and .bib files

**Keys.** `Paper::cite_key` is the paper's BibTeX key, used by every BibTeX output (Copy BibTeX, exports,
the share panel's .bib, the MCP `cite` tool, kept .bib files) and by `Library::latex_cite` (`\cite{a,b}`).
It starts as `export::cite_key` of the details (first author's family name, year, first word of the title,
accents folded to ASCII) with `a`, `b`, … after it when another paper has that key (compared without case).

- **Stored in the log:** a `set_cite_key` op fixes a paper's key. It is written when a paper is added (if it
  has an author and a year; otherwise once it has them), when a key is first used (BibTeX, `\cite`, a .bib
  file), when the user changes it (`set_cite_key`: letters, digits and `- _ : . + /`, unique), and before a
  local edit or deletion would change a key that isn't fixed yet. So a key never changes because the title or
  authors were edited or another paper was deleted. Older versions skip the op (an unknown `op` doesn't
  parse) and never rewrite another device's log, so they don't lose it.
- **The same on every device:** keys are worked out in `State::assign_cite_keys` from the logs alone:
  fixed keys first (if two devices gave the same key to different papers before seeing each other's logs,
  the earlier claim keeps it, by time, device and paper id); then papers without one (libraries from before
  keys, papers added by older versions) take their base key and the first free suffix, in the order they
  were added. Devices with the same logs compute the same keys, and two devices that fix the same paper's key
  at once write the same value. The rare case that still moves a key: two devices offline giving the same
  key to different papers; the later one becomes `…a` once they sync.

**.bib files.** **Keep BibTeX File Updated…** on a folder or All Papers (Mac: `apple/Mac/BibFiles.swift`;
desktop: `desktop/src-tauri/src/bibfiles.rs`) links it to a file. After a change to the library (local, or
synced from another device) the linked files are rewritten after a 1.5 s pause: the folder's papers (not
its subfolders') sorted by key, written atomically, and only when the text changed (no churn for Dropbox,
Git or Overleaf). A folder that isn't in the library, or an empty library, leaves the file as it was. The
links are per device (Mac: user defaults; desktop: `settings.json`), never in the synced library.

**Entry types.** `PaperMeta::work_type` keeps what kind of work a paper is, in Crossref's words
(`journal-article`, `proceedings-article`, `book-chapter`, `book`, `posted-content` for preprints,
`report`, `dissertation`, `dataset`, `standard`…), and `series` the book series of a chapter or
proceedings volume. Both are filled when details are fetched (Crossref's `type`; its container titles
split into the book and the series, "Lecture Notes in Computer Science" being the series; arXiv:
`posted-content`; Europe PMC: source PPR is a preprint; OpenAlex's type) and from BibTeX and RIS
imports. Older logs have neither (serde default, `#[uniffi(default = "")]`), and older versions skip
them. When it is empty `worktype::kind` infers the kind: an arXiv / bioRxiv… journal or a preprint DOI
is a preprint; "Proceedings of…", "Conference", "Symposium", "Workshop" or "Lecture Notes…" a
conference paper (PNAS, Proc. R. Soc., Proceedings of the IEEE and the PACM journals excepted);
otherwise a journal makes an article. From the kind:

| Kind | BibTeX | RIS | CSL |
|---|---|---|---|
| journal article | `@article` (journal) | JOUR | article-journal |
| conference paper, LNCS chapter | `@inproceedings` (booktitle, series, publisher) | CPAPER / CHAP (T2, T3) | paper-conference / chapter |
| other chapter | `@incollection` | CHAP | chapter |
| preprint | `@misc` (howpublished = {arXiv preprint arXiv:…}, eprint, archivePrefix) | JOUR / GEN | article (publisher, number arXiv:…) |
| report, standard | `@techreport` (institution) | RPRT / STAND | report / standard |
| thesis | `@phdthesis` (school) | THES | thesis |
| book | `@book` (series, publisher) | BOOK | book |

The built-in styles cite conference papers and chapters "In *Proceedings…*" with pages and publisher.
BibTeX is written with accented letters as LaTeX (`Pawe{\l}`, `Pregui{\c{c}}a`), which every engine and
font prints; organizations ("World Wide Web Consortium") are braced whole.

**Titles in BibTeX** (`export::bib_title`). Only what must stay as written is braced, each word on its
own, so the bibliography style decides the case of the rest (most styles that change case, such as
`plain`, `unsrt` and `acm`, put titles in sentence case): acronyms and words with capitals inside or
with digits (`{GROBID}`, `{arXiv}`, `{iPhone}`, `{PDFFigures}`, `{BRCA1}`, `{Qwen3}`, `{RNA}-seq`, `{AI}-Powered`),
and, in a title in sentence case (as Crossref often has them: more longer words in lower case than
capitalized, leaving out the first word, the first after a colon and title case's small words), the
capitalized words after its start, which are then proper nouns (`{Bayesian}`, `{Sweden}`). Proper nouns in
a title in title case can't be told from the other words and are left to the style ("The Semantic
Reader Project" becomes "The semantic reader project" in `unsrt`, as an unbraced hand-written entry
would). Lunta used to brace whole titles (`{{…}}`), which froze Crossref's sentence case and title case
alike, whatever the style; there is no option to go back to that: a style that keeps the case as given (the
standard biblatex styles) prints the title as it is either way, and a title can still be given braced
whole as one of the paper's own fields (`set_bib_fields`, below).

**Long author lists.** A paper with more than 15 authors is written with its first 10 and `and
others`, which BibTeX and biblatex styles print as "et al." (Qwen3's 60 authors, Apple's 156). The
library's setting (`Library::set_bibtex_options`, `export::BibtexOptions { max_authors, shown_authors }`,
`max_authors` 0 never shortens; Mac: Settings › Shorten long author lists in BibTeX) is kept in the log
(op `set_bibtex_options`, the latest wins; older versions skip it), so every device writes the same .bib
files. RIS and the citation styles are not affected (the styles shorten lists their own way).

**Proceedings titles.** Crossref's titles of ACM proceedings sometimes have a stray "on" ("Proceedings of
the 16th ACM/IEEE-CS on Joint Conference on Digital Libraries"); `worktype::fix_proceedings_title` drops it
when every word between "Proceedings of the" and "on" is an ordinal, a year or an acronym and a
conference, symposium, workshop or congress follows ("Proceedings of the ACM on Programming Languages", a
journal, and "… Workshop on …" stay). Applied as details come in and in exports. Acronyms such as
"(JCDL)" or "(CHI)" are never added: Crossref doesn't have them and a guessed one could be wrong (a .bib
imported with its keys keeps the researcher's booktitle, below).

**Capitals and subtitles.** Crossref's subtitle is joined to the title with ": ". A title with at
least 80% capitals (10+ letters, 3+ words: "A NEW MEASURE OF RANK CORRELATION") is put in title
case, keeping words with digits (BRCA1, COVID-19), common acronyms and Roman numerals; name parts in
capitals ("KENDALL") in proper case, initials kept. This happens when details come in (so **Fill In
from the DOI** fixes a paper) and, for papers already in the library, in exports only (BibTeX, RIS,
citations): the library is not rewritten.

**Importing a .bib with its keys.** **File › Import BibTeX (Keep Citation Keys)…** (Mac; also in a
folder's menu), **+ › Import BibTeX (Keep Citation Keys)** (iPhone, iPad), `Library::import_bibtex_keep_keys`
(core/src/bibimport.rs) for the other apps. Each entry is found by its DOI, its arXiv id (eprint, or
"arXiv:…" in the journal) or Crossref's bibliographic search (`refcite::resolve_reference`, title and
year checked), else added from its own fields; gaps in the record are filled from the .bib (an LNCS
volume). The paper (merged with one already in the library) goes into the folder with the entry's key
as its citation key, so `\cite{oldkey}` keeps working; a key another paper has, an invalid key, or a
second entry for the same paper is reported, not forced. Entries that aren't papers (`@misc`,
`@online`, `@software` without DOI, arXiv id or journal) are kept as written with the folder (op
`collection_bib`, the latest wins; older versions skip it) and written after the papers into the
folder's kept .bib (`Library::kept_bibtex`, which the Mac and desktop .bib files use), so one file has
every key. The report gives the counts (by DOI, arXiv, Crossref search, as is, kept as written) and
lists where the .bib and the record found differ: year, title, pages, number of authors ("and others"
allowed), first author, DOI. `cargo run --example bib_keep_keys -- refs.bib out.bib` does it in a
throwaway library.

What the researcher wrote wins where the record can't know better:
- **DOI.** A DOI in the .bib is kept, never replaced by the one a lookup found (Crossref's search may find
  JSTOR's record, 10.2307/…, of a paper whose publisher's DOI the .bib has); the difference is reported.
- **Given names.** Where the .bib's are fuller than the record's for the same family name in the same
  place ("Maurice G." for "M. G.", "Daniel S." for "Daniel"), the paper gets the .bib's.
- **The paper's own BibTeX fields** (`bibimport::own_fields`, op `set_bib_fields`, the latest wins; older
  versions skip it; `Library::bib_fields` / `set_bib_fields`): an author field that is one organization or a
  name braced whole (`{Qwen Team}`, `{Apple}`) or ends in `and others`; the booktitle of an
  `@inproceedings` / `@incollection` (with its "(CHI)" or "(ECDL 2009)"); and fields the library has no
  place for: `type` (`W3C Recommendation`), `note`, `addendum`, `edition`, `editor`, `address`,
  `organization`, `month`, `isbn`, `issn`, `chapter`, `language`. They are kept as written (LaTeX and inner
  braces; a value that is a @string macro is left out) and in every BibTeX output of the paper (kept .bib
  files, Copy BibTeX, exports) replace Lunta's field of the same name or are added after its fields. The
  library keeps the record's details (all 60 authors of Qwen3, for the reader and the citation styles).

Tests: `cargo test keys` and `cargo test thin_details` in `core` (stable keys across exports, uniqueness,
edits and deletes, user keys, two library instances syncing through copied logs) and
`cargo test bibfiles` in `desktop/src-tauri`; `cargo test worktype`, `cargo test bibimport`,
`cargo test exports_by_work_type`, `cargo test bibtex_letters`, `cargo test bibtex_titles`,
`cargo test bibtex_long_author_lists` and `cargo test proceedings_titles` in `core` (types, capitals,
subtitles, braces, author lists, the .bib import with stand-in lookups: DOI, given names and own fields kept).

## Checks against the published record

Lunta proposes, the researcher decides: these checks report and suggest; the library changes only
when a choice is confirmed, through the change log like any other edit (`core/src/checks`).

**Check a Reference List** (`checks::refcheck`). Input: a .bib, a .ris, a pasted list (numbered, one
paragraph each, or author–year lines; a line that is indented, unfinished or doesn't start with an
author joins the one before), a paper's own reference list (its reading view's `ol.refs` and the other
lists the References panel reads, `Library::paper_reference_list`; else the PDF's after its last
References heading, `pdf_reference_list` from the app's PDF lines), or a folder's papers. Each
reference is looked up:

1. by its DOI: Crossref, then DataCite (arXiv, Zenodo…), then doi.org's handle API (registered with
   another agency: exists, details not compared);
2. by its arXiv id;
3. else Crossref's bibliographic search, then OpenAlex (title, ±1 year), then PubMed (Europe PMC,
   `SRC:MED`). A hit is taken only when the title is the reference's (nearly all its words, a
   "RETRACTED:" mark ignored), the years are at most one apart and the first author agrees (or the
   title is long and specific).

The record is compared field by field: title (a left-out subtitle is fine), first author, number of
authors ("and others" allowed; a group author such as "Qwen Team" not compared), year, venue
(abbreviations and initials: "Nat. Neurosci.", "J Biol Chem", "PNAS"; a conference's short name in
brackets), volume, first page, DOI. For a pasted reference the found record's author, year, volume and
pages are looked for in its text. Results: **verified**; **minor differences** (the fields, as given and
as found); **not found**, worded "Could not be found in Crossref, OpenAlex or PubMed" and nothing
stronger (books, reports, theses and very new papers are often missing); **DOI points to a different
work** (what it points to, and the reference's own DOI when its details find it) or nowhere; not
looked up (software, web pages: `bibimport::is_extra`); couldn't be checked (a service couldn't be
asked: never reported as not found). Retractions and corrections on the work found are listed. The
report (`RefCheckReport`) has the totals, a summary line, Markdown with links and CSV.
`cargo run --example check_refs -- refs.bib [out.md] [out.csv]` runs it from the command line.

**Retractions and corrections** (`checks::updates`). Crossref keeps update relations: notices
deposited by publishers and, since Crossref took over the Retraction Watch database (2023), each of its
records, as `updated-by` on the work (`type`: retraction, partial_retraction, withdrawal, removal,
expression_of_concern, correction, erratum, corrigendum, addendum, clarification…; `source`:
`publisher` or `retraction-watch`; `updated` the date; the notice itself has `update-to`, and
`filter=update-type:retraction` lists notices). The library's DOIs are asked 20 at a time
(`/works?filter=doi:A,doi:B…&select=DOI,type,updated-by,relation`); the two sources' records of one
notice are joined.

**Published versions of preprints** (papers whose kind is a preprint: `posted-content`, an arXiv,
bioRxiv, medRxiv… DOI or journal), in order: Crossref `is-preprint-of` on the preprint (in the same
batch), `has-preprint` on the article asked in reverse (`filter=relation.object:…`), bioRxiv's and
medRxiv's `api.biorxiv.org/pubs/<server>/<doi>` (`published_doi`), arXiv's `<arxiv:doi>` and
`<arxiv:journal_ref>` (`id_list`, 20 at a time), OpenAlex locations (a `publishedVersion` in a journal or
conference with a DOI), and last Crossref's search (the same title, the same first author, not
earlier, an article, conference paper or chapter). A published paper is never offered its preprint,
and a version found that is itself a preprint is not offered.

**What is kept.** `PaperUpdates` (notices; the published version to suggest; a linked one; a declined
DOI; after a switch the preprint's details and when) in a new op, `set_updates` (the latest wins),
written only when something changed. Older versions skip the op (an unknown `op` doesn't parse), so
they show nothing and lose nothing; a newer one reads it on every device. It is not in `PaperMeta`, so
an edit of the details on an older device can't wipe it. `Library::all_paper_updates` gives it for the
list's badges, the reader's banner and the smart folders "Retracted or corrected" and "Published since
you added them" (`updates` in smart-folders.json: `flagged` / `published`, optional, so older
folders still read).

**Choices.** Switch to the Published Version (`use_published_version`, after a confirmation): the
published record by its DOI becomes the paper's details (the preprint's abstract, keywords and arXiv id
fill gaps); highlights, notes, tags, folders and the citation key stay (the key is guarded as for any
edit); `undo_published_version` restores the preprint's details. Then, on the Mac, iPhone and iPad, the
published version's full text when it is open access: its reading view replaces the preprint's only if
every highlight is found in the new text (as Use This Page's Full Text does), a PDF only if the old one
has no highlights; otherwise the new files are kept as a backup. Link Both keeps the preprint and shows
the published version with it; Keep the Preprint stops suggesting that version.

**When, and politely** (`checks::net`). On demand (a paper's menu; the library's File or + menu),
and weekly: `check_paper_updates_if_due` (per device, the whole library) a minute after the app
starts and every six hours after. One request at a time per service with a pause (arXiv 3 s, Crossref
250 ms, bioRxiv 500 ms, OpenAlex 150 ms), User-Agent `Lunta (https://github.com/christoffermattssonlangseth/lunta)`
without an e-mail address, 429 and 5xx answered by waiting (Retry-After, at most a minute). Answers
are kept in the device's cache (`checks/answers.json` a day for reference lists,
`checks/updates.json` six days for the weekly check, an hour on demand; "no such thing" is kept,
errors are not), and batches are asked in a fixed order so the same library asks the same questions.

| | Mac | iPhone, iPad | Windows, Linux | Android |
|---|---|---|---|---|
| Check a Reference List | File menu; a folder's menu (Check References); a paper's menu | + menu; a paper's menu (Check) | the import menu; a folder's menu; a paper's menu | + menu |
| Report | sheet; Share, Save as Markdown / CSV | sheet; Share, Save | dialog; Save as Markdown / CSV | dialog; Share (Markdown, CSV) |
| Retractions, published versions | badge, reader banner, smart folders, File › Check Library… | badge, reader banner, smart folders, + menu | badge, banner in the details, smart folders | + menu, summary with the choices |

MCP: `check_references(text | bibtex, markdown?)` and `library_status(id?)`, both read-only.

Tests: `cargo test checks` in `core`, on answers recorded from the services (`src/testdata/checks`, no
network): a .bib with a verified reference, minor differences, one not found, a wrong DOI, a
retracted paper and software; a pasted numbered list; a library's retraction and a bioRxiv preprint's
journal version (and nothing for an arXiv preprint or a published paper with an arXiv id); a second
check that writes nothing; another device reading the same; switch, undo, link both, keep the
preprint; the answer cache and the pacing. `cargo test checks -- --ignored record_check_fixtures`
asks the services and records the answers again (and is the live test). `cargo test refcite`: a PDF's
whole reference list.

## Tidy the library and Outline from Highlights

Both follow the checks' rule: **Lunta proposes, the researcher decides.** Suggestions are listed to approve one by one
or all at once; nothing changes until then, and what is applied goes through the change log (synced). Tags, folders and
DOIs that were applied can be undone (`TidyChange` → `undo_tidy_change`); a merge deletes papers, so the apps ask first.
The prompts and heuristics live in the core so every app proposes the same.

**Tidy** (`core/src/tidy/`; Clean Up Library on the Mac, iPhone and iPad, Tidy Library on Windows, Linux and Android):

- *Duplicates* (`duplicates.rs`): the same DOI (normalized); the same title allowing small differences (Dice ≥ 0.9 on
  words, punctuation, accents, a subtitle left out) with the same first author, years at most one apart and no two
  different DOIs; a preprint and its published version (title Dice ≥ 0.7, same first author, not earlier, or the
  published DOI the checks found). Pairs come from shared rare title words, not every pair. Each group names the paper to
  keep (the published version, else the most complete). `merge_papers(keep, others)` fills empty details, moves tags,
  folders, star, read and Must Read state, highlights and notes, a PDF, reading view or full text the kept paper lacks,
  and a fixed citation key, then deletes the others. A preprint whose published version is *not* in the library is
  listed with the checks' Switch to the Published Version (`use_published_version`), not handled here.
- *Missing details*: no DOI (articles, conference papers, chapters, preprints), no PDF (the apps' Find PDF), no reading
  view (Make Reading Views). `find_missing_dois` (`doi.rs`) gives an arXiv paper its arXiv DOI without asking anyone,
  otherwise asks Crossref's bibliographic search (title, first author, year; through the checks' polite, cached `Net`)
  and takes a record only when the titles agree (`refcite::title_in` both ways, or a subtitle left out), the years are
  at most one apart, the first author is among its authors and a published paper isn't given a preprint's DOI. A DOI
  another paper already has is marked as a duplicate to merge. `apply_doi_suggestions` sets the DOI and fills empty fields.
- *Topics* (`groups.rs`): up to ten tags or folders to make, each with its papers ("Spatial transcriptomics — 34
  papers"). Without a model: title words and two- and three-word phrases, keywords and the abstract's start, kept when
  several papers share them (≥ 3 and ≥ 2 %, ≤ 50 %, mostly in titles or keywords), scored by coverage and specificity, a
  word giving way to its phrase, picked so that no two cover mostly the same papers, plus journals with many papers;
  names of existing tags and folders are left out. With a model: `tidy_topic_prompt(max_papers)` lists the latest titles
  by number (60 for Apple's on-device model, 150 for Qwen3 4B via MLX, about 110 on Windows and Linux, whose model runs with a 4096-token context), the model answers `Topic: 3, 8, 15`, and
  `tidy_groups_from_answer` keeps only numbers from the prompt, topics of two papers or more, no vague names
  ("Other", "Methods"). `create_groups(…, as_folders)` makes the ticked ones (a folder of the same name is reused).
- *Existing tags for untagged papers*: a tag whose name is in the paper's title or keywords, or whose papers share
  distinctive terms with it (at most two per paper, with why).
- Dismissed suggestions ("Not Duplicates", `doi:<id>`, `tag:<id>:<tag>`, `topic:<name>`) are kept in the device's cache.

**Outline from Highlights** (`core/src/outline.rs`): the highlights and notes of a set of papers (a folder with its
subfolders, a tag, a search's results, a selection), optionally about a topic, as Markdown: a heading per theme, a point
per highlight with its quote word for word, or the researcher's note marked *Note:*, cited `([Kukanja et al. 2024](lunta://open?id=…), [@Kukanja2024cellular])`
(2019a/2019b when two labels are alike), then the Sources (APA, citation key, link). Without a model the themes are the
papers, and within a paper the reading view's sections (the headings before each highlight) or the PDF page; with a topic,
only the highlights that mention it (all, with a note, when none does). With a model, `outline_prompt(ids, topic,
max_items)` numbers the highlights (30 for Apple's model, 100 for Qwen3 via MLX, about 50 on Windows and Linux) and asks for `Theme:`, `Summary:`, `Items:`;
`outline_from_highlights(ids, topic, prompt, answer)` takes the themes and numbers only, puts each highlight once, keeps
what the model left out under Other highlights, and marks the one-line summaries as the model's. The model never writes a
point. `outline_check` verifies an outline: every point must be a highlight's quote or a note; the tests also feed it
invented, altered and paraphrased points. Copy Markdown, Save as .md, and on the Mac (and iPhone, iPad) Copy as Rich Text
(the outline's HTML).

**Summarize Highlights** (`core/src/outline/summary.rs`): the same highlights and notes (with a topic, those that
mention it) condensed by the on-device model, Short (3–5 sentences) or Longer (6–10), as Prose or Bullet points, every
sentence ending with the highlights it is based on (`… iron-laden microglia [1, 4].`). `summary_plan(ids, topic, length,
style, max_items, max_parts)` numbers them [1]…[n] (quote, author–year, section; 25 per prompt for Apple's model, 45 for
Qwen3 on phones and Android, about 50 on Windows and Linux; at most 6 parts, what doesn't fit is said); more than fit one
prompt are cut paper by paper into parts, each numbered 1…k in its prompt (`ModelPrompt.ids` maps back), summarized in
2–4 sentences, then `summary_combine_prompt` gives the parts' checked sentences, with the original numbers, to the model
to combine. `summary_from_answers` checks every sentence in code: split into sentences (bullets, "et al.", "Fig. 2",
"e.g.", decimals and a citation after the full stop handled); dropped when it cites nothing, cites a number that wasn't
given (combining: one the parts didn't cite), or isn't supported by the highlights it cites (fewer than 60 % of its
content words in them, word endings allowed; a number not in them; a negation they don't have); repeats kept once. How
many were dropped and why is said; when nothing holds up there is no summary (`ok` false) and the apps show the outline
with that note. If combining gives nothing usable, the parts' sentences are shown. Citations are renumbered 1, 2… in the
order first cited; Markdown (and HTML for rich text): the summary, "*Written by the on-device model from your
highlights. Check it against the quotes below.*", **Highlights cited** footnote style (`[2] “quote” — [Kukanja et al.
2024](lunta://open?id=…&highlight=…)`) and the Sources. `lunta://open?id=<paper>&highlight=<annotation>` opens the paper
at the highlight on the Mac. `Library::summary_with_model` (feature `llm`) runs it all with `AiEngine`. MCP has no model:
no summary there (an agent can summarize `outline_from_highlights` itself, quoting it).

UI: Mac: Clean Up Library window (Lunta menu) with the suggestions under the duplicates; Outline from Highlights… in a
folder's and a tag's menu, the papers' menu (the selection) and the File menu (the papers listed, so a search's).
iPhone and iPad: Clean Up Library… in the library's list; Outline from Highlights… in a folder's and a tag's menu and the
list's ⋯ menu. The on-device model is Apple's or Qwen3 via MLX (`AskEngine.plainAnswer`); without one the heuristics.
Windows, Linux and Android: see their sections; they run Qwen3 through `tidy_topics_with_model` and `outline_with_model`.
Summary: the outline sheet's Outline | Summary switch (Mac, iPhone, iPad: `SummaryView.swift`; also from the iPhone
reader's ⋯ › Outline from Highlights…), Length and Style, Summarize / Regenerate; the summary with its citation numbers
tappable (the quote, Open in Paper: the reader at the highlight, `HighlightJump`), the cited quotes below, Copy Markdown,
Copy as Rich Text, Share, Save as .md. Without a model the Summary side says why (the assistant's availability texts:
Apple Intelligence on macOS/iOS 26, the open model on 27). Windows and Linux (`outline.ts`, `summary_make`) and Android
(`OutlineUi.kt`, `HighlightsOutline.summarize`) the same with Qwen3; without the downloaded model they point to
On-Device AI in the settings.

MCP: `outline_from_highlights(ids | collection | tag, topic?)`, read-only, by paper and section (the agent may regroup
the points, keeping the quotes). No Summarize Highlights: MCP has no model.

Tests: `cargo test tidy outline` (duplicates by DOI and by a title that differs a little, preprint pairs, merging, DOIs on
Crossref answers recorded in `testdata/tidy/` — `cargo test tidy -- --ignored record_tidy_fixtures` re-records them —, the
guard, topics and tag suggestions without a model, the model's answers, the outline's Markdown, citations, sections and
the no-invented-text check).

## Releases

Push a version tag: `git tag v0.2.0 && git push origin v0.2.0`. GitHub makes the release and attaches the
Windows and Linux installers and the Android APK (`.github/workflows/release.yml`); then, on a Mac,
`scripts/release-mac.sh v0.2.0` builds the Mac app, signs it with Developer ID, has Apple notarize it
and attaches it (`--check` does all but the upload).

The Android APK is signed with the release key `~/.lunta/lunta-android-release.jks` (alias `lunta`; its
password is in the macOS Keychain as "Lunta Android release key"), which the release job gets from
the repository secrets `ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASSWORD`. Every update must be
signed with the same key, so **keep a backup of the key file and its password** somewhere safe. The same
job builds the Google Play bundle (`Lunta-<version>-Google-Play.aab`: the same app, key and version code,
without the updater) and attaches it too; Play App Signing uses this key as well
([Google Play](google-play.md)). Its
SHA-256 fingerprint: `E3:B3:4F:21:4A:50:95:CF:F7:6A:4F:AA:19:CE:1B:51:A8:EF:CD:42:8A:45:C2:55:14:D1:AD:21:F6:C9:BB:41`.

### Updates

The apps from GitHub Releases update themselves from **the latest release** (the iPhone and iPad app
is updated by the App Store and has none of this):

| App | How | Feed on the release | Signed with |
|---|---|---|---|
| Mac | Sparkle 2 (`apple/Mac/Updates.swift`; Lunta › Check for Updates…, the switch in Settings) | `appcast.xml` | EdDSA key in the login Keychain of the Mac that releases (Sparkle `generate_keys --account lunta`); public key `SUPublicEDKey` in `project.yml` |
| Windows, Linux AppImage | tauri-plugin-updater (`desktop/src-tauri/src/updates.rs`, `desktop/src/updates.ts`; Settings ▾) | `latest.json` | minisign key `~/.tauri/lunta-updater.key` (password in `~/.tauri/lunta-updater.password`); public key in `tauri.conf.json` |
| Android | the app asks GitHub's API for the latest release (`android/…/update/`; Settings) | none: the release and its APK | the APK release key above (Android installs an update only with the same key) |

Each checks at most once a day (on by default; a switch in each app's settings) and on demand. The
Linux .deb can't replace itself: it offers the release page. Android's updater is a build flag
(`lunta.selfUpdate`, on; the Google Play build sets it to false, which also leaves out the
REQUEST_INSTALL_PACKAGES permission: see [Google Play](google-play.md)).

**Once:** put the Tauri key in the repository secrets (the desktop release builds fail without them):

```sh
gh secret set TAURI_SIGNING_PRIVATE_KEY < ~/.tauri/lunta-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD < ~/.tauri/lunta-updater.password
```

Keep copies of both private keys somewhere safe, as with the Android key: without them no installed
copy can be updated again. The Sparkle key: `apple/build/SourcePackages/artifacts/sparkle/Sparkle/bin/generate_keys --account lunta -x <file>`
exports it (`-f <file>` imports it on another Mac).

**Each release** (as above, plus):

1. The tag's release starts with the previous release's `latest.json` and `appcast.xml` (so the apps
   never find no feed), then `release.yml` replaces `latest.json` once the desktop builds are attached
   (`scripts/update-feeds.sh desktop`, from the installers' `.sig` files).
2. `scripts/release-mac.sh vX.Y.Z` builds the Mac app with the tag's version and a build number
   from the time (`YYYYMMDDHHMM`, UTC: what Sparkle compares, and larger than the `YYYYMMDDn` numbers
   in `project.yml`), attaches the zip and then `appcast.xml`, signed with `sign_update` (the Keychain
   may ask to allow it the first time).
3. After writing the release notes (`gh release edit vX.Y.Z --notes-file …`), run
   `scripts/release-mac.sh --notes vX.Y.Z`: it puts them (the part above "Which file do I need?") into
   both feeds. Android reads them from the release directly.

`DRY_RUN=1 scripts/update-feeds.sh mac vX.Y.Z <zip>` prints a feed instead of attaching it.

**Testing an update** (needs a published release newer than the copy you test with):

- **Mac:** keep an older notarized build (e.g. from `scripts/release-mac.sh --check` before tagging, or
  the previous release's zip once it has Sparkle) in a scratch folder, open it there, Lunta › Check for
  Updates…: it offers the release, installs it over that copy and reopens it. Delete the copy afterwards
  and unregister it (`lsregister -u <path>`), so only `/Applications/Lunta.app` stays registered.
  Debug builds never check by themselves.
- **Windows / Linux:** install the previous release (AppImage on Linux), or build an older version
  without the private key (the app only needs the public key to check what it downloads):
  `npx tauri build --bundles appimage --config '{"version":"1.0.0","bundle":{"createUpdaterArtifacts":false}}'`;
  run it, Settings ▾ › Check for Updates…, Install and Restart.
- **Android:** install an older APK signed with the release key, e.g.
  `LUNTA_VERSION_NAME=1.0.0 ./gradlew :app:assembleRelease` (with the key in `local.properties`),

### PDFium (PDF conversion in the Rust converter)

The Rust converter reads PDFs with [PDFium](https://pdfium.googlesource.com/pdfium/) through
`pdfium-render` (feature `pdf`, on by default for `cargo build/test/run`, off in
`scripts/build-core.sh`: the Apple apps convert PDFs with PDFKit and never need PDFium). PDFium is
loaded when the first PDF is converted, from the first of:

1. `PDFIUM_PATH`: the library file, or the folder holding it;
2. next to the executable (or in `../lib`, `../Frameworks`, `../Resources`, `lib` from it);
3. the system library search path.

If none has it, converting a PDF fails with a message saying so; everything else still works.
Nothing is downloaded at build time and no binary is in the repository. Prebuilt libraries:
[bblanchon/pdfium-binaries](https://github.com/bblanchon/pdfium-binaries/releases) (tested with
`chromium/8152`; `pdfium-render` is built for the 8125+ API). For local work, e.g. on a Mac:

```sh
mkdir -p ~/pdfium && curl -L https://github.com/bblanchon/pdfium-binaries/releases/latest/download/pdfium-mac-arm64.tgz | tar xz -C ~/pdfium
PDFIUM_PATH=~/pdfium/lib cargo run --release --bin paper2epub -- --offline paper.pdf out/
```

How apps should ship it (include PDFium's `LICENSE`, BSD-3-Clause, and its `licenses/`):

- **Windows:** `pdfium-win-x64.tgz` (or `-arm64`); put `bin/pdfium.dll` next to the app's `.exe`.
- **Linux:** `pdfium-linux-x64.tgz` (`-arm64`; `-musl-x64` for Alpine); put `lib/libpdfium.so`
  next to the executable, or in the AppImage/Flatpak `lib/` (also found via `LD_LIBRARY_PATH`), or
  point `PDFIUM_PATH` at a distribution-installed copy.
- **Android:** `pdfium-android-arm64.tgz` (plus `-arm`, `-x64` for other ABIs); put `libpdfium.so`
  in `jniLibs/<abi>/`. The app's native-library folder is on the linker path, so it is found as a
  system library.
- **macOS (outside the Apple apps):** `pdfium-mac-arm64.tgz` / `-x64`; `libpdfium.dylib` in
  `Contents/Frameworks` of a bundle, or next to a command-line binary.

`P2E_DEBUG=1` prints the analysed paragraphs (same format as Paper2EpubKit's); `P2E_DEBUG_LINES=<page>`
and `P2E_DEBUG_CHARS=<page>` dump PDFium's lines and characters for one page.

### Browser extension

Chrome → `chrome://extensions` → Developer mode → Load unpacked → `extension/`. Lunta (for Mac,
Windows or Linux) must be running; the extension talks to it on `127.0.0.1:47480` (extension
requests only; `/cite/…` for citing in Google Docs, above): `apple/Mac/ExtensionServer.swift` on the Mac, `desktop/src-tauri/src/extension.rs`
in the desktop app (same endpoints; "Use this page's full text" through `core/src/pagetext.rs`,
with the page readers ported to `core/src/convert/webpage.rs` and friends; backups of replaced
reading views in the app's data folder, `backups/`). A debug desktop build takes another port from
`LUNTA_EXTENSION_PORT`; on macOS, where the port is Lunta for Mac's, the desktop app opens the
endpoint only then.

**Safari.** The same files are the Safari extension: `LuntaSafariMac` (embedded in LuntaMac) and
`LuntaSafari` (embedded in LuntaiOS) copy `extension/` into the extension's bundle at build time
(`apple/SafariExtension/copy-extension.sh`; only the manifest is adjusted: the app's version, the
service worker only, no Firefox settings, and `nativeMessaging` on iPhone and iPad). Turn it on in
Safari › Settings › Extensions (Mac; a development build needs Develop › Allow Unsigned Extensions,
the Developer ID–signed release doesn't), or Settings › Apps › Safari › Extensions › Lunta on the
iPhone and iPad (allow it on all websites).

- **Mac:** exactly like Chrome: 127.0.0.1:47480, Origin `safari-web-extension://`.
  `SafariWebExtensionHandler` is unused there.
- **iPhone and iPad:** there is no server on the device. `background.js` asks the native handler
  (`browser.runtime.sendNativeMessage`, `{op: "ping"}` → `{platform: "ios"}`) and then sends the same
  requests to it instead: the handler only writes files (an extension has little memory): each
  request goes into the App Group, `SafariInbox/.staging/<token>/` in pieces of ≤ 512 K characters,
  then is moved to `SafariInbox/<ms>-<token>/` (`request.json` + the page, its figures, the PDF) in
  one step; "status" is answered from `SafariInbox/index.json`, which the app writes whenever the
  library changes, plus the requests still waiting ("✓ Sent · Open Lunta" in the panel). The app
  does them when it becomes active or is opened with `lunta://safari`
  (`apple/Shared/SafariInboxImport.swift`: save → add the paper, pdf → attach it,
  fulltext → `usePageFullText` in `apple/Shared/PageFullText.swift`, the same as on the Mac, with
  the highlight check and the backup in the app's own Application Support/Lunta/backups). Figures
  are capped lower than on the Mac (40, 6 MB each, 30 MB in all). The format is in
  `apple/Shared/SafariInbox.swift`.
- **Testing the hand-off without a device:** a Debug Mac build plays recorded messages through the
  same handler code and import into a scratch library:
  `Lunta -testLibrary <dir> -extensionPort 47498 -testSafariInbox <script.jsonl>` (answers in
  `<script.jsonl>.out`; the line format is described at `runSafariInboxScript`). The messages can be
  recorded from the real `background.js` in node with a stand-in for `browser.runtime.sendNativeMessage`.

## Google Drive sync

`core/src/drive/` (cargo feature `drive`, on by default for desktop and the CLI, and in the Apple build: for a Mac, iPhone or iPad whose library lives in Google Drive (see [Where the library lives on Apple devices](#where-the-library-lives-on-apple-devices)), and for the Mac's bridge: **Lunta › Also Sync with Google Drive…** keeps the iCloud library and the Drive folder in sync)
syncs a library through Google Drive's API, for devices that have no synced folder: the Android app,
Linux, or anyone who prefers it. It uses **the same layout** as everything else (see
[Library layout](#library-layout-sync-safe)), in a Drive folder called `Lunta`. Lunta reaches only the
files it created there (Google's `drive.file` scope, see [Access](#access-drivefile-only)), so devices share
the folder through the API (Android, the Mac bridge, the CLI), not through Google Drive for desktop.

```
 working folder (the Library opens it)  <-- Syncer -->  RemoteStore: GoogleDrive | LocalDirRemote
```

**How it syncs** (details in `core/src/drive/syncer.rs`):

- Each device writes only its own `ops/<device>.jsonl` and `positions/<device>.json`. The syncer uploads
  its own log (the whole file, when it grew), downloads the others', and **never uploads or modifies
  another device's log**. If the remote copy of the device's own log holds lines the local one lost
  (reinstall with the same device id), they are merged back, never dropped.
- `papers/<id>/*` is synced both ways, keyed by paper id: new or changed files go up or down, and a file
  deleted on one side is deleted on the other (unless the other side changed it since: an edit beats a
  delete). A paper file is written once or replaced whole, so there is nothing to merge.
- Shared root files (`smart-folders.json`, `watches.json`, `foryou.json`, any `*.json`): last writer wins by
  modification time. The overwritten local copy is kept under `.lunta-sync/conflicts/`.
- Paper files are transferred before positions and logs, so another device never sees an op for a paper whose
  files are not there yet. State is saved every few transfers: an interrupted sync resumes where it stopped
  (files already identical by md5 cost nothing).
- **Incremental**: a small state file remembers each file's remote id, md5, size and modified time and the
  local size and mtime. The first sync lists the Drive tree; later syncs use the Drive **changes** API (one
  request per 1000 changes, includes deletions) instead of listing, because a folder's `modifiedTime` is not
  reliable for "something inside changed". Local files are hashed only when size or mtime moved. Files up to
  5 MB are uploaded in one multipart request, larger ones with a resumable session in 8 MiB chunks. Deletes
  go to the Drive trash.
- Safety nets: it refuses to apply more than half of the tracked files (or more than 10) as deletions in one
  run, and refuses an empty remote after files were synced before.
- **Lazy files** (`SyncOptions::lazy`): PDFs, EPUBs and narration are left on Drive during a sync;
  `Syncer::fetch_paper(id, kinds)` / `fetch_file(path)` download them on demand, e.g. when the Android app
  opens a paper (`paper_files(id)` lists what exists remotely, `remote_paper_files()` the whole library).
  A big file that is only on the remote is never a deletion: never downloaded, or its download removed with
  `remove_download(id)` ("Remove Download": deletes this device's copies of the paper's PDF, EPUB and
  narration that the remote has unchanged, keeps copies with changes not uploaded yet, and records them as
  not here). Deleting a downloaded file any other way is still a deletion. `Library::set_remote_files(paths)`
  makes the files that are only on the remote count as present (`has_pdf`/`has_epub`, `file_status` =
  `InCloud`), like iCloud's placeholders.

**API** (plain owned types, ready for UniFFI; not exported to Swift yet):

```rust
let auth = Authenticator::new(OAuthClient::from_env()?, Arc::new(FileTokenStore::new(tokens_path)));
auth.connect_loopback(&|url| open_browser(url), Duration::from_secs(300))?;   // desktop / CLI
// Android: OAuthClient::authorization_url(redirect, &Pkce::generate()?, state), open a Custom Tab,
// then Authenticator::complete(code, verifier, redirect). Tokens go through the TokenStore trait, so
// each platform keeps them in its own keychain / keystore.
let drive = GoogleDrive::new(auth, DriveRoot::default());          // folder "Lunta" in My Drive, or DriveRoot::Id(..)
let syncer = Syncer::new(library_dir, device_id, Box::new(drive), SyncOptions::new(state_path))?;
let report = syncer.sync_now()?;     // SyncReport { uploaded, downloaded, deleted_*, conflicts, errors, changed, .. }
syncer.status();                     // offline: pending uploads/downloads, remote-only files, last sync
library.refresh()?;                  // when report.changed
```

`LocalDirRemote` (a folder as the remote) implements the same trait and is what the tests use.

**CLI** for trying it by hand (`--state-dir` defaults to `<library>/.lunta-sync`, which holds the tokens,
the sync state and a generated device id):

```sh
export LUNTA_GOOGLE_CLIENT_ID=...apps.googleusercontent.com LUNTA_GOOGLE_CLIENT_SECRET=...
cd core
cargo run --bin lunta-sync -- connect --library ~/lunta-test     # opens the browser
cargo run --bin lunta-sync -- sync    --library ~/lunta-test [--lazy]
cargo run --bin lunta-sync -- status  --library ~/lunta-test
cargo run --bin lunta-sync -- fetch <paper-id> --library ~/lunta-test
# no Google account? any folder works as the remote:  --remote-dir /some/folder
```

### Where the library lives on Apple devices

The first time Lunta opens on a Mac, iPhone or iPad it asks **Where should your library live?**: iCloud Drive,
Google Drive or only on this device. The choice is kept in `UserDefaults` (`libraryStorage`:
`icloud` | `googleDrive` | `device`), and `CloudLibrary.resolve()` opens that place:

| Choice | Library folder | Sync |
|---|---|---|
| iCloud Drive | the app's container, `Documents/Library` | iCloud (as always) |
| Google Drive | `Application Support/Margins/DriveLibrary` | `DriveLibrarySync` ↔ the "Lunta" folder in Drive |
| Only on this device | `Application Support/Margins/Library` | none |
| (not set: used Lunta before the choice existed) | iCloud when available, else the local folder | as before |

**What start-up does** (`StartupDecision.decide`, `apple/Shared/StorageDecision.swift`, tested by
`node --test apple/storage-tests/`, which compiles it with a Swift test driver):

- A stored choice: open it.
- Lunta ran here before (the device id `deviceID` is in `UserDefaults`) or the local folder has change logs:
  open the automatic way, as before. Existing users never see the question, and are never moved.
- iCloud available: look in the iCloud folder for change logs (up to ~12 s, "Looking for your library in
  iCloud…"; a new device may take a moment to get the listing). Found: open it, remember iCloud, and say so
  once ("Your library is in iCloud", with **Use Google Drive Instead…**). Not found: ask, iCloud recommended.
- No iCloud: ask, Google Drive recommended (iCloud is shown greyed with how to turn it on).

Choosing Google Drive signs in first (`ASWebAuthenticationSession`, the same OAuth client and redirect
`com.googleusercontent.apps.<id>:/oauth2redirect` as Android and the bridge; the session catches the redirect,
so the scheme isn't in Info.plist). The text about Google's "unverified app" warning is
`GoogleDriveClient.unverifiedNote` (`DriveLibrarySync.swift`): set it to nil once Google has verified Lunta.

**Google Drive sync on Apple devices** (`DriveLibrarySync`): the core's Syncer in normal (not bridge) mode,
`LibrarySync.google_drive_also_own`, with tokens and state in `Application Support/Lunta/`
(`google-tokens-library.json`, `drive-library-state.json`; excluded from backups on iOS) and the picked folder in
`UserDefaults` `driveLibraryFolderId`. It syncs at start, when the app comes to the front (unless it synced in the
last minute), every 5 minutes, and 20 s after this device's change log grows; a sync that is running when the
iPhone app goes to the background gets the background time iOS allows.

*Download papers when you open them* (`DriveLibrarySync.onDemand`, `UserDefaults` `driveDownloadOnOpen`; on by
default on iPhone and iPad, off on the Mac; a switch in Library Storage and the Mac's Settings › Library):
the sync is lazy, so a paper's PDF, reading view and narration stay in Drive until needed; change logs,
metadata, full texts, summaries, Pencil drawings and reading positions always come down. Either way the files
not here count as present: while the library opens (`DriveLibrarySync.preload`, from the sync's records,
offline) and after each sync, download or removed download, `remote_paper_files()` goes to
`Library.setRemoteFiles`, so nothing offers Find PDF or remakes a reading view for them, and `LibraryModel.remoteOnly`
gives the lists their cloud marks. Every file read goes through `LibraryModel.fetchFile` / `ensureLocal`
(`needsDownload` for "Downloading from Google Drive…"), which fetches from Drive (`fetch_paper`, off the main
thread) what isn't here; the readers show a failure with Try Again; Share says which files couldn't be
downloaded. Per paper: Download / Remove Download (context menu, paper info); Library Storage: how much is here
and in Drive, Download All, Remove Downloads Not Opened in 30 Days… (`driveFilesUsed` remembers when each
paper's files were last asked for). Switching on deletes nothing; switching off downloads the rest at the
next sync. Moving a library out of Google Drive downloads what's only in Drive first. iCloud mode is
untouched (its placeholders go through the same helpers as before). The Mac writes the files only in Drive to
`~/Library/Application Support/Lunta/remote-files.json` (with the library root) for lunta-mcp, which doesn't
download them itself (no Drive sign-in there, and two syncs of one folder would race): full texts are always
there, so `read_paper` and search see every paper; `get_paper` lists `not_downloaded`, `find_pdf` doesn't
replace a PDF that's in Drive, and `add_highlight` says the reading view isn't downloaded. The Mac's AI agent (lunta-mcp) writes its own
log (`ops/agent-….jsonl`) into the library folder; `SyncOptions::also_own` makes the Mac upload it like its own.
lunta-mcp finds the library through `~/Library/Application Support/Lunta/library-root`, which the Mac app writes
whenever it opens one. Status: Library Storage, and a line at the bottom of the Mac's sidebar / the iPhone's
**Library Storage…** row. The Mac's bridge (Also Sync with Google Drive…) does nothing while the library itself
lives in Google Drive.

**Moving the library** (Mac: Settings › Library › Change…, the **Library Storage** window; iPhone/iPad:
**Library Storage…** at the end of the library's list): `LibraryMover` signs in first if moving to Google Drive
(on a Mac whose bridge is connected it takes the bridge's sign-in and folder), syncs a Google Drive library once
more, then `LibraryLocation.copyLibrary` copies `ops/`, `positions/`, `papers/` and the root `*.json` files to the
new folder: what the destination lacks is copied, this device's (and its agent's) change log is merged line by
line when both have it, nothing else is overwritten, and files still in iCloud are downloaded first. The old copy
is never changed or deleted; the app says where it is. If any file can't be copied the move stops and nothing
changes. Then the choice is stored and the library reopened: the Mac restarts Lunta (its servers hold the
library), the iPhone and iPad open it in place. Moving an iCloud library to Google Drive takes only this device
out of iCloud; the Mac offers **Keep iCloud and Also Sync with Google Drive** (the bridge) instead, and on iPhone
and iPad the dialog says that's done by a Mac.

Not done yet: background sync (BGAppRefreshTask) on iPhone and iPad; the Share and Safari
extensions write to the App Group inbox as before, so they work with any choice.

### Access: `drive.file` only

> **Not switched on yet.** `NARROW_DRIVE_ACCESS` in `core/src/drive/auth.rs` is `false`: sign-in still asks for
> the full `drive` scope, and no adoption runs, until the Windows and Linux app syncs through the Drive API
> (today it shares the library through a Google Drive for desktop folder, whose new files `drive.file` can't
> see). Everything below describes the behaviour once it is on; the tests run with it on.

Lunta asks Google for **`https://www.googleapis.com/auth/drive.file`** and nothing else: it sees only the
files and folders created by the Cloud project's OAuth clients, plus the items the user picks for it in
Google's picker. That scope is *non-sensitive* (brand verification only, no security assessment, no
"unverified app" screen once verified). The full `drive` scope (all of the user's files) is *restricted*
(a yearly CASA assessment, and 100 users until verified); older versions asked for it.

**Who talks to Drive, and how** (Cloud project `lunta-514610`):

| Platform | OAuth client | Drive calls |
|---|---|---|
| Android (`AppModel.kt`, `SyncWorker.kt`) | the "iOS"-type client `340661790250-jvrurg…` (`lunta.googleClientId`, redirect `com.googleusercontent.apps.…:/oauth2redirect`, Custom Tab + PKCE) | through the core's `LibrarySync.google_drive` (lazy) |
| Mac bridge (`apple/Mac/DriveBridge.swift`) | the same client (`ASWebAuthenticationSession`) | through `LibrarySync.google_drive_bridge` |
| Mac, iPhone, iPad with the library in Google Drive (`apple/Shared/DriveLibrarySync.swift`) | the same client (`ASWebAuthenticationSession`) | through `LibrarySync.google_drive_also_own` (lazy on iPhone/iPad by default, a setting on the Mac; the Mac adds its AI agent's log) |
| CLI `lunta-sync` | any client of the project (`LUNTA_GOOGLE_CLIENT_ID`, a "Desktop app" client with its secret; loopback redirect) | `GoogleDrive` + `Syncer` |
| Windows/Linux desktop app | none: it opens a library *folder* (e.g. inside Google Drive for desktop); no Drive API | — |
| Google Docs extension / Mac (citations) | separate scope `auth/documents` (see google-docs-extension.md); no Drive API | — |

The core's Drive client (`core/src/drive/gdrive.rs`) makes these calls, all under the library folder:
`files.list` (`'<folder>' in parents`, 20 parents per query, and `name = 'Lunta' and 'root' in parents` to
find the folder), `files.get` (folder metadata; a changed file's parents; `alt=media` downloads),
`files.create` (folders; multipart and resumable uploads), `files.update` (new content of a file it
uploaded; `trashed: true` for deletes; parents and name only during adoption), `files.copy` (adoption only),
`changes.getStartPageToken` and `changes.list` (incremental syncs). No `permissions` calls, nothing outside
the library folder (adoption also writes one backup folder in My Drive, see below). With `drive.file`,
`files.list` and `changes.list` simply leave out what the app can't see.

`drive.file` access belongs to the **Cloud project**, not the client: what the Mac bridge creates, Android
sees, and the reverse (they use one client anyway). It is per item: a picked folder is granted, the files
already inside it are not (Google's docs say nothing either way; developers report it, and the picker for
apps grants exactly the ids it returns). Files the app created inside it are visible regardless.

**How the folder is found.** By id first: the folder of the last sync (kept in the sync state's cursor),
or the folder chosen in the picker (`DriveRoot::Id`, saved by the app); only a device that has never
synced looks for "Lunta" in My Drive by name (and creates it if there is none it can see). A folder known
by id that can no longer be opened gives the error `FOLDER_NOT_VISIBLE` ("Lunta can't open its folder in
Google Drive …"; `drive_folder_not_visible()` for the apps) instead of quietly starting a second, empty
"Lunta" folder; the apps then offer **Choose your Lunta folder**.

**Who creates the files.** Android, the Mac bridge and the CLI create the folder and everything in it
through the API, so a library made by them is fully visible. Not visible with `drive.file`: anything put
into the folder by another app: Google Drive for desktop (a Windows/Linux desktop app or a Mac whose
library folder is inside it), files dropped in through drive.google.com, or a "Lunta" folder made by hand.

**Choose your Lunta folder** uses Google's picker for desktop and mobile apps ("OnePick"): the normal
authorization URL plus `trigger_onepick=true&allow_folder_selection=true&allow_multiple=true`
(`OAuthClient::picker_url`, `DriveAuth::begin_pick`), opened in the same Custom Tab /
`ASWebAuthenticationSession` as sign-in, with the same redirect. The redirect carries `picked_file_ids`
next to the `code` (`DriveAuth::picked_ids_from_redirect`); after the token exchange the first picked
folder (`DriveAuth::picked_folder`) becomes the library (Android: `Settings.driveFolderId`; Mac:
`UserDefaults` `driveFolderId`). It needs the Picker API enabled in the project, no API key, and only
works with `drive.file`. Chosen alternatives: the web Picker in a Custom Tab needs a hosted page and an API
key; Android's Storage Access Framework with the Drive provider gives content URIs, not Drive API access;
"Open with" needs the Drive UI integration (`drive.install`) and grants one file at a time.

**Moving existing users over (adoption).** Tokens keep the scopes they were granted, so a phone or Mac
signed in by an older version still has the full scope after the update (`Tokens.scope`, recorded from
the token response; a token saved without it came from the full scope). While it does, a full listing first
**adopts** the library (`GoogleDrive::adopt`): every item is checked with `isAppAuthorized`;
- a foreign **file** gets an app-created copy (`files.copy` with the same name, folder and
  `modifiedTime`), and the original moves (`files.update` with `addParents`/`removeParents`, not deleted)
  to "Lunta (originals from before the update)" in My Drive, under the same path;
- a foreign **folder** (folders cannot be copied) gets an app-created twin with the same name in the same
  place, its children move into it, and the emptied original goes to the backup folder;
- a foreign **library folder** (a "Lunta" made by hand or by Drive for desktop) is replaced the same way:
  a new "Lunta" in the same place takes its contents, and the old one, renamed "Lunta (originals from
  before the update)", becomes the backup folder;
- Google Docs and other native files are left alone (they are not part of a library).

Ops logs are copied byte for byte under their own names, so the sync protocol does not change: ids change,
md5s don't, so no device transfers anything again. The cursor records `adopted`; until a run adopts
everything (a failed item stays where it was, is reported and retried at the next sync) every sync with the
full scope lists and adopts again, and with the full scope a change from another app (Drive for desktop
adding a file) also triggers a listing and adoption. With `drive.file` adoption is never needed (and would
see nothing). The report's `notices` say what happened ("Lunta made its own copies of 3 file(s)… the
originals are in …"), shown under Sync on Android and in the Mac's Google Drive window. Afterwards the apps
offer **Sign in again**, which replaces the token with a `drive.file` one (no revoke needed).

**Disconnect no longer revokes the grant**, only forgets the tokens on the device: with `drive.file`,
revoking the grant removes the project's access to the files it created, for every device (they share
the grant), and signing in again does not give it back. (`lunta-sync disconnect --revoke` still can.)

**Limits.**
- After the switch, what other apps add to the folder is invisible to Lunta, for good. In particular the
  Windows/Linux desktop app, which keeps its library in a synced folder (Google Drive for desktop), does
  not share with Android or the Mac bridge through the API any more for anything it *creates* (its own
  op log, new papers); edits to files Lunta created stay visible. Until the desktop app syncs through the
  API itself (the core's `Syncer` is ready for it), one device still on the full scope keeps adopting
  those files.
- Two devices adopting at the same moment can copy the same file twice; the duplicate is harmless (same
  name and content; the syncer uses one and says "two files with this name").
- A library in a *shared drive* or shared by another account was never supported and is not now.

### Setting up Google Cloud (once, by you)

Lunta ships **no** Google credentials; you create an OAuth client in your own project.

1. [console.cloud.google.com](https://console.cloud.google.com) → new project → *APIs & Services* → *Library* →
   enable the **Google Drive API** and the **Google Picker API** (for "Choose your Lunta folder").
2. *Google Auth Platform* → *Branding*: app name "Lunta", support e-mail, logo, home page, privacy policy
   (`site/app-privacy.html`) and terms; *Audience*: user type *External*. *Data access* → *Add or remove
   scopes*: tick **`.../auth/drive.file`** ("See, edit, create and delete only the specific Google Drive files
   you use with this app"), nothing else. It is non-sensitive, so the app can go *In production* and only
   needs brand verification.
3. *Credentials* → *Create credentials* → *OAuth client ID*:
   - type **Desktop app** (CLI): gives a client id and a client secret. Put them in
     `LUNTA_GOOGLE_CLIENT_ID` / `LUNTA_GOOGLE_CLIENT_SECRET`. (A desktop client's "secret" is not confidential;
     Google still requires it at the token endpoint.)
   - type **iOS** (what the Mac bridge and the Android app use: it allows the app's own redirect scheme,
     `com.googleusercontent.apps.<id>:/oauth2redirect`; no secret), or **Android** (package name and the
     SHA-1 of the signing key).
   All clients must be in the same project: `drive.file` access is per project.
4. `lunta-sync connect` and sign in.

**Moving the existing project (`lunta-514610`) from `drive` to `drive.file`** (the author, once):

1. Ship the apps with this change first (Android and the Mac), and let them sync once on each device that
   was signed in before: that adopts the folder while the old tokens still have the full scope. Removing the
   scope from the console does not take it away from tokens already granted, but don't rely on that for
   long: see 5.
2. *APIs & Services* → *Library* → **Google Picker API** → *Enable*. No API key is needed for the picker for
   apps (the OAuth client is enough); if you ever add a web picker, create a key under *Credentials*, restrict
   it to *Google Picker API* and to the site's HTTP referrer.
3. *Google Auth Platform* → *Data access*: remove `https://www.googleapis.com/auth/drive`, add
   `https://www.googleapis.com/auth/drive.file`, *Save*.
4. *Verification center*: submit for (brand) verification. The scope justification for `drive.file`:
   "Lunta is a reference manager. It keeps the user's library (paper metadata, PDFs, reading views,
   highlights) in a 'Lunta' folder in their Google Drive and syncs it between their devices (Android, and
   a Mac that bridges it to iCloud). It reads and writes only the files it creates in that folder, and a
   folder the user chooses for it in Google's picker; it never accesses other files." Usually no demo
   video is needed for non-sensitive scopes; if asked, record sign-in, the consent screen, a sync and the
   folder in Drive.
5. Tell users signed in before the update to tap **Sign in again** (Android: Settings sheet; Mac: Lunta ›
   Also Sync with Google Drive…), which replaces the restricted grant with `drive.file`. Users who don't keep
   working on the old token until it is revoked or expires.

**Scope in code.** `auth::Scope::File` is the default everywhere; `Scope::Full` remains for the CLI
(`--scope full`) and for recognising old tokens.

Tests: `cargo test` covers the syncer with a folder as the remote (a Mac-like device writing straight
into it plus API devices: adds, edits, highlights, deletes, paper files, shared-file conflicts, interrupted
and resumed syncs, lazy downloads, safety nets) and the Drive client against an in-memory mock of the Drive

```sh
LUNTA_GOOGLE_CLIENT_ID=... LUNTA_GOOGLE_CLIENT_SECRET=... \
LUNTA_TEST_TOKEN_FILE=<state-dir>/google-tokens.json LUNTA_TEST_DRIVE_FOLDER=<id of an empty scratch folder Lunta made> \

```

(With `drive.file` the scratch folder must be one Lunta created or picked: e.g. `lunta-sync sync --folder-name
lunta-scratch` on an empty library, then take the id from Drive's URL. Never use a real library or account.)
The mock (`core/src/drive/mock.rs`) imitates `drive.file` too: items remember whether the API created
them or the user picked them, and with `file_scope` on nothing else exists for the client. The tests
`drive_file_*` and `migration_*` cover a new library, an existing app-made one (found by id even when
renamed), a foreign folder (not visible; picking the folder is not enough, picking its files is), a lost
folder (an error, not a new folder), and adoption with the old token (copies, originals kept, nothing
trashed, nothing transferred again, then a `drive.file` token and a new device see everything).

The Android app uses it through UniFFI (`core/src/drive/ffi.rs`: `DriveAuth` for sign-in, `LibrarySync`
for the Syncer, also with a plain folder as the remote for testing). Not done yet: wiring into the desktop

## Desktop app (Windows and Linux)

`desktop/` is a [Tauri 2](https://tauri.app) app: a Rust backend that calls the core directly (no
UniFFI) and a web frontend in plain TypeScript with Vite (no UI framework: the app is a sidebar, a list
and a details pane, and the reader is plain DOM anyway, so a framework would mostly add weight). It also
runs on macOS, for testing.

- **Library folder:** chosen on first run (a folder in Google Drive for desktop, Dropbox or OneDrive to
  share the library with other computers; any local folder otherwise) and remembered with a per-install
  device id (`windows-1a2b3c4d`, `linux-…`) in the app's config folder. Like the apps, it writes only
  its own `ops/<device>.jsonl` and `positions/<device>.json`, and picks up other devices' changes
  every ten seconds. The search index lives in the app's cache folder. (To share with the Mac and
  iPhone, the library must be in a folder all of them sync; the Apple apps use iCloud Drive.)
- **Reading view:** the paper's EPUB is unpacked by the core and served to an iframe through the app's
  `lunta://` scheme, with the Apple apps' own reader CSS and scripts injected (extracted from the Swift
  by `scripts/extract-reader-assets.mjs`, run before every `npm run dev`/`build`; CI fails if they are
  stale). `desktop/src/reader/bridge.js` stands in for WKWebView's `window.webkit.messageHandlers`
  (posting to the app window) and for `evaluateJavaScript`. Highlights and notes go through the core's
  op log, positions into `positions/`, so both sync with the Mac and iPhone.
- **Organising:** select several papers in the list (⌘/Ctrl-click, Shift-click, ⌘/Ctrl-A). Drag papers
  (the whole selection if you drag one of them) onto a folder in the sidebar to add them to it
  (membership, not a move), or onto a tag to tag them; drag a folder onto another folder to nest it,
  or onto the Folders heading for the top level. The target lights up while you drag. (Done with
  mouse events rather than HTML5 drag and drop, which Tauri's file-drop handling breaks on Windows.)
- **Edit Details…** (button in the details, or the paper's context menu) edits title, authors,
  journal, date, volume/issue/pages, publisher, identifiers, abstract and keywords through the core,
  and can fill them in from the DOI. **Smart folders** are created with ＋ next to Smart Folders and
  edited or deleted from their context menu; same rules and `smart-folders.json` as the Mac app.
- **Security:** a content security policy is set in `tauri.conf.json` (own scripts only, the reader
  iframe and images from `lunta://`, PDF.js worker from blob:/self, IPC). Debug runs of the packaged
  frontend: `npm run build`, then `cargo build --features tauri/custom-protocol` in `src-tauri`
  (plain `cargo build` loads the Vite dev server, which has no CSP).
- **Citing in Word** (Windows; Word on the web on Linux too): **Settings ▾ › Citations in Word & Google Docs…**,
  served on https://localhost:47481 as on the Mac; see [Word on Windows and Linux](#word-on-windows-and-linux).
- **Adding papers** uses the core's metadata lookup and the Rust converter (`core/src/convert`). It
  can't analyse PDFs yet, so a paper whose only full text is a PDF gets no reading view (the converter's
  reason is shown); its PDF still opens.

Build and run (needs Rust and Node 20+; on Linux also `libwebkit2gtk-4.1-dev libgtk-3-dev
libayatana-appindicator3-dev librsvg2-dev patchelf`; on Windows the WebView2 runtime, already on
Windows 10/11):

```sh
cd desktop && npm install
npx tauri dev                           # run
# with the updater's signatures: TAURI_SIGNING_PRIVATE_KEY(_PASSWORD) set (see Updates); without:
#   add --config '{"bundle":{"createUpdaterArtifacts":false}}'
npx tauri build --bundles msi,nsis      # Windows installers → src-tauri/target/release/bundle/
npx tauri build --bundles appimage,deb  # Linux packages
npx tauri build --bundles app           # macOS, for testing
```

`.github/workflows/desktop.yml` builds the Windows and Linux installers on GitHub Actions.

For scripted UI checks, debug builds run any `*.js` dropped into `$LUNTA_DEV_EVAL_DIR` in the window
(which then stays hidden unless `LUNTA_DEV_SHOW=1`) and, on macOS, can save a snapshot of it
(`dev_snapshot`). None of this is in release builds.

Not in the desktop app yet (the Mac app has them): highlighting in the PDF (PDF highlights made on the
Mac or iPhone are listed, not drawn), reading views from PDFs, adding a paper from a PDF alone,
import (Papers, BibTeX, RIS), Discover,
Clean Up, Ask's proposals (tag, add…) and the MCP server; Make Natural Narration (no AAC encoder
everywhere: a narration made on the Mac or Android plays).

## Listen on Windows, Linux and Android

As in the Apple apps (`apple/Shared/Narrator.swift`): the reading view's narration items (`narration.js`) are read in
order, the one being read highlighted and followed, a tapped paragraph read from; previous / next paragraph, next
section, speed (0.8–2×), voice; it goes on when the reader closes (Now Playing in the library).

- **Text** (`core/src/tts/text.rs`): Apple's `Narrator.spoken` rules, plus author–year citations, then cut into sentence
  pieces (≤ 300 characters; the first of a paragraph ≤ 60 so speech starts soon).
- **Natural voice:** Kokoro-82M v1.0 (Apache-2.0) as packaged by sherpa-onnx, through sherpa-onnx's C API loaded at
  run time (`core/src/tts/engine.rs`, libloading): nothing is linked at build time, so CI builds as before. sherpa-onnx
  **v1.13.8**, the last that reads words its lexicon lacks (numbers, acronyms) with espeak-ng (v2 skips them); the
  full-precision model (the int8 one is 2.5× slower on Apple silicon). The Apple apps' eight voices, `af_heart` default.
  Download (`install.rs`, only from sherpa-onnx's GitHub releases, pinned by size and SHA-256, checked before unpacking):
  the model, 350 MB (about 380 MB on disk, English files and espeak-ng-data only), into the app's local data folder;
  on Windows and Linux (and macOS, for testing) also sherpa-onnx's library, 8–13 MB. On Android the library comes in
  the APK (`scripts/fetch-sherpa-onnx-android.sh`, run by `build-core-android.sh`: libsherpa-onnx-c-api.so and
  libonnxruntime.so, about 27 MB per ABI before compression). Settings deletes it.
- **Speed** (M1 Pro, 4 threads; `cargo run --release --example tts_bench -- <folder>` measures it): model loaded in
  1.2 s, a 79-character first sentence in 1.4 s, then 4× faster than real time (RTF 0.25). Pieces are made three
  ahead of the one playing. Phones: not measured; expect slower (RTF around 0.5–1 on recent ones).
- **Without the natural voice:** the system's voice (desktop: the web view's speech synthesis, Windows' voices;
  WebKitGTK's where it has one; Android: TextToSpeech), with an offer to download it.
- **Desktop** (`desktop/src/listen.ts`, `src-tauri/src/listen.rs`): 🎧 in the reader; WAV pieces in an `<audio>`
  element (speed by playbackRate); media keys through the web view's media session. Linux plays audio through
  GStreamer (the .deb depends on gstreamer1.0-plugins-good).
- **Android** (`app/lunta/listen/`): ⋯ › Listen; pieces streamed into one AudioTrack (no gaps; the highlight follows
  the frames heard); `ListenService`, a media3 `MediaSessionService` (foreground service type `mediaPlayback`), gives
  the media notification, lock screen and headset controls and background playback; audio focus, pausing when
  headphones are unplugged. ⋯ › Make Natural Narration renders the paper (`NaturalVoice.render`) and encodes it as
  AAC (MediaCodec) into `narration.m4a` + `narration.json`, the Mac's format, so it syncs and plays everywhere.
- **Made on the Mac:** a paper with `narration.m4a` + `narration.json` plays that, following its timing map, on
  every platform.
- Tests: `cargo test tts` in `core` (text, pieces, download checks with a fake archive, timings);
  `LUNTA_TTS_DIR=<folder> cargo test tts -- --ignored` speaks with a downloaded voice.

## Android app

`android/` is a native app in Kotlin with Jetpack Compose and Material 3 (teal and copper, light and
dark, an adaptive icon made from `design/logo-1024.png`) on the Rust core through UniFFI's Kotlin
bindings. It follows the iPhone app's Mail-style layout.

- **Setup:** on first run, choose where the library lives: **Google Drive** (sign in with a Custom Tab
  and PKCE through the core's `DriveAuth`, `drive.file` scope; the library is a "Lunta" folder in your Drive,
  in sync with a Mac through its bridge; Settings has **Choose your Lunta folder…** (Google's picker) and, for a
  token from an older version, **Sign in again**) or **a local library** on the phone (for trying it out). Drive sync is lazy: it runs on start,
  on pull-to-refresh and about every 30 minutes (WorkManager), and fetches a paper's EPUB or PDF
  when you open it.
- **Library:** places (All, Starred, Unread with counts, New for You, folders as a tree,
  smart folders written by the Apple apps, tags) each opening a paper list with full-text search and
  sort; swipe from the right edge for star, read/unread and Folders & Tags. The paper page has the
  abstract, folders and tags, APA / Vancouver / Nature citations (copied), **Read**, Add PDF from Files
  (the system picker), Find PDF, Make reading view and delete (with confirmation).
- **Adding:** by DOI or link (core lookup and the Rust converter, PDFs through PDFium), a PDF from
  Files, or the share sheet of other apps (links, DOIs and PDFs).
- **Reader:** a WebView with the Apple apps' reader CSS and scripts (extracted from the Swift by
  `scripts/extract-reader-assets.mjs`, copied into the APK by Gradle); `android/app/src/main/assets/reader/bridge.js`
  stands in for `window.webkit.messageHandlers` (`addJavascriptInterface`). Text size, scroll or page
  turning (swipe or tap the edges), highlights in four colours with notes, a highlights list, contents,
  and the reading position, synced through `positions/` like the other apps. The PDF opens in a
  PdfRenderer view (no PDF highlights yet; ones made elsewhere are listed).
- **New for You** (`app/lunta/foryou/`, on the core's `NewForYou`; see [New for You](#new-for-you-on-windows-linux-and-android)):
  the place in the library with the count of new papers; the feed (status and refresh, "In short" with links to its
  papers, cards with Add (long-press: Add as Must Read), More Like This, Not for Me, share, Earlier), a paper's page
  (abstract, why it's here, Add to Library / Must Read / Show in Library); the settings sheet (paragraph and Draft from
  My Library with the on-device model, ORCID iD and people you publish with, the morning time, papers a day, preprints,
  what you follow, journal names looked up on OpenAlex). Adding goes through Add Paper's DOI path (the feed's details
  when there is no DOI or the lookup fails). In the app a due run starts when the library opens, with the on-device
  model when it is downloaded and allowed (searches, screening), then summaries and the digest. In the background
  `ForYouWorker` (WorkManager, every 6 hours with a network) syncs, makes the day's feed when it is due (without the
  model), syncs again and posts "New for You · 5 papers" (channel "New for You", once per feed, not after the feed was
  opened; tapping opens it). On Android 13+ the notification permission is asked when New for You is first shown with
  something to follow, and again from Save; refused, there is the count in the library.

Build and run (JDK 21, Android SDK with platform 36, build-tools 36.0.0 and NDK 28, Rust with the
`aarch64-linux-android` target, `cargo install cargo-ndk`):

```sh
scripts/build-core-android.sh              # core → android/app/src/main/jniLibs, Kotlin bindings, PDFium (downloaded)
cd android && ./gradlew :app:installDebug  # with a device or emulator attached
echo 'lunta.googleClientId=<id>.apps.googleusercontent.com' >> android/local.properties   # for Google sign-in
```

`ABIS="arm64-v8a x86_64"` also builds for x86_64 emulators. The OAuth client is an "Android" client in
Google Cloud (package `app.lunta`, the SHA-1 of the signing key; see [Google Drive sync](#google-drive-sync));
without an id the app builds and explains what is missing. Debug builds can start straight on a local
library, optionally synced with a plain folder as the "remote":
`adb shell am start -n app.lunta/.MainActivity --es lunta.setup local --es lunta.remoteDir <dir>`
(`cargo run --example seed_library -- <dir> <doi>...` makes a library of public papers for it).
`.github/workflows/android.yml` builds the debug APK on GitHub Actions.

Not in the Android app yet: highlighting in the PDF, Discover, Ask about the library, import,

## On-device AI (Windows, Linux, Android)

The Summary card and Ask, which the Apple apps run on Apple's on-device model (or Qwen3 4B through MLX),
run in the desktop and Android apps on an open-weights model through llama.cpp, in the core
(`core/src/llm/`, cargo feature `llm`, on for the desktop app and the Android build, off for Apple's):

- **Model:** Qwen3 (Apache-2.0) as GGUF, 4-bit (Q4_K_M), pinned to a revision on Hugging Face and checked
  against its SHA-256 (`llm/models.rs`). Windows and Linux: Qwen3 4B from Qwen's own `Qwen/Qwen3-4B-GGUF`
  (2.5 GB). Android: Qwen3 1.7B (1.3 GB) from llama.cpp's `ggml-org/Qwen3-1.7B-GGUF` (Qwen publishes the
  1.7B only as Q8_0, 1.8 GB and slower on a phone). Never bundled: downloaded when the user turns the
  feature on (desktop: Settings ▾ › On-Device AI…; Android: Settings › On-device AI), into the app's local
  data folder (`<local app data>/models`; Android's no-backup folder), as `<file>.part` resumed with a
  Range request, renamed only once its checksum matches; deletable there.
- **Runtime:** [llama-cpp-2](https://crates.io/crates/llama-cpp-2) (llama.cpp built from source by CMake;
  needs CMake and libclang). CPU only: x86-64 with AVX2/FMA (checked before loading: an older processor
  gets a note instead of a crash), Android arm64 for ARMv8.2 with dot products (`GGML_CPU_ARM_ARCH` in
  `scripts/build-core-android.sh`; checked too), Metal on a Mac (the desktop app on macOS, for testing).
  Vulkan would speed up PCs with a GPU but is not built (its SDK and shader compiler on every CI runner).
  Qwen3's chat template (ChatML) with thinking off (the empty think block `enable_thinking=False` writes),
  4,096 tokens of context.
- **Summary card:** the Apple apps' own card and source (`luntaSummarySource`, now also extracted to
  `desktop/src/reader/generated/summary.js` and injected on Android), the same prompt and cleaning rules
  as `SummaryWriter.swift` (`llm/prompt.rs`), and the same `summary.json` next to the paper, with the same
  source hash (SHA-256 of the 1,900-word source): a summary made on any device is shown on the others
  (it syncs like the paper's other small files, also in the Android app's lazy sync), and one made from a
  different reading view is made again. The card's note says which model wrote it, and that it can be wrong.
- **Ask:** one call, no tools: the app looks up first and gives the model just that. About a paper: its
  five passages of `fulltext.txt` that best match the question (BM25, words as prefixes, a follow-up looked
  up with the question before it), the abstract and the user's highlights; the answer cites them as [n],
  with the passages listed under it. About the library (desktop): the papers a search for the question's
  words finds (all words, else each word, fused), with their abstracts, and the library's counts, tags and
  folders. Not ported: the Apple apps' tools and proposals (tag, add to folder, add a paper), which need a
  model that calls tools reliably. New for You's searches, screening, summaries and digest: see New for You below.
- **Android's memory rule:** `ActivityManager.MemoryInfo.totalMem` (a 6 GB phone reports about 5.3–5.6 GiB):
  6 GB or more, offered; 4–6 GB, offered after a warning ("needs at least 6 GB; this phone has 4 GB… try
  anyway"); less, or not arm64-v8a, or no dot-product instructions: shown with the reason, no download.
- **Speed** (the summary of a 630-word source, ~900 tokens of prompt): on an M-series Mac's CPU (5 threads)
  Qwen3 1.7B 11 s, 4B 16 s; with Metal 3.3 s and 5.5 s. Expect a few times slower on a phone's CPU.

```sh
cd core && cargo test --features llm llm::                          # prompts, cleaning, summary.json, downloads (mock HTTP)
cargo run --release --features llm --example ai -- download desktop|phone <dir>
node scripts/summary-source.mjs book.epub > source.txt               # what the card is made from
cargo run --release --features llm --example ai -- summarize <model.gguf> source.txt "<title>"
LUNTA_TEST_GGUF=<model.gguf> cargo test --release --features llm llm::tests::real_model -- --ignored --nocapture
```

`LUNTA_LLM_CPU=1` keeps llama.cpp off the GPU (to time the CPU on a Mac); `LUNTA_LLM_LOG=1` keeps its log.
Google's on-device Gemini Nano (ML Kit GenAI) was not used on Android: its API is in beta and runs on
few phones.

## New for You on Windows, Linux and Android

The Apple apps' daily feed (`apple/Shared/Watches.swift`), ported to the core (`core/src/foryou/`) so the
desktop and Android apps have it too, on **the same files**:

- **Shared state:** `<library>/foryou.json` (the paragraph, settings, ORCID iD, the feed, Add / More Like This /
  Not for Me feedback, what was offered) and `<library>/watches.json` (journals, authors, papers, topics you follow),
  read and written in Swift's Codable format (`state.rs`: every non-optional key written, a nil optional left out,
  dates as `.iso8601` without fractions, keys a newer app adds kept). Each change re-reads the file, changes it and
  writes it back whole (through a temporary file), as the Swift does; the file itself is last-writer-wins (iCloud
  Drive, a synced folder, or the Drive syncer's rule for root `*.json`). So a feed made on the Mac shows on Android
  and the other way round, and a paper turned down anywhere is gone everywhere. What only one device keeps (when
  the feed was last opened there, the last notification) is `foryou-local.json` in the app's own folder, as the Apple
  apps keep it in UserDefaults. The Apple apps need no change to share it.
- **The run** (`run.rs`, WatchCenter.run): searches written from the paragraph; OpenAlex for those, for your watches,
  for papers citing your papers (with your ORCID iD, leaving out your own) and the newest papers in the library;
  bioRxiv and medRxiv's last days by keyword; then only papers new to you (not in the library by DOI or title, never
  offered, not yours, an abstract, no data deposits or theses); ranking; screening; the feed (newest picks on top,
  80 kept, 3,000 offered keys remembered). Due at the morning time, local time; whichever device runs first makes the
  day's feed (a phone leaves the first two hours to a computer, as the iPhone does).
- **When a source fails** (both apps): a request that fails is no longer taken for "no new papers". If every
  OpenAlex request fails, no feed is made, nothing is marked as offered, the day's run stays due (tried again at
  the next check) and the feed says "Couldn't reach OpenAlex" with the reason and Retry instead of "Nothing new
  today"; if some fail (or bioRxiv/medRxiv), the feed is made and the failures are said above it. The problem is
  kept on the device only (`foryou-local.json` `problem`/`failed`/`problemAt`; `WatchCenter.problem` on Apple)
  and hidden once a later run, here or on another device, made a feed.
- **OpenAlex's daily allowance**: OpenAlex charges requests against a daily allowance: without an API key one
  allowance ($0.10/day, 1,000 credits; a search costs 10, a filtered list 1, a lookup by id 0) is shared by
  everyone behind the network's address (a university, a phone carrier's shared address), with a free key the
  user has their own ($1/day). A day's run costs about 140 credits. Used up, OpenAlex answers 429 with
  `"reason": "daily_budget"` and a Retry-After of hours: `metadata::get_text` (and Check Citations' client) no
  longer waits and retries then, but says "OpenAlex's free daily allowance for your network is used up (it renews
  …). A free OpenAlex API key (in New for You's settings) gives Lunta its own." The key (Settings › OpenAlex) is
  kept in foryou.json (`openalexKey`, so every device has it) and set process-wide (`set_openalex_key`), so every
  OpenAlex request in the app carries it. Journal and author names are resolved to OpenAlex ids once per app run
  (a search each). `cargo run --example foryou_diag -- <copy of a library folder>` runs the stages on a copy and
  logs every request, what each filter dropped, and the candidates.
- **Ranking** (`rank.rs`): the Swift formula (0.55 × paragraph + 0.35 × the three closest library papers, ± 0.25 for
  papers you added or turned down, + 0.3 for More Like This; + 0.15 for what you follow, + 0.06 for journals you
  follow, up to + 0.04 for new papers), on TF-IDF vectors of words and word pairs: Apple's sentence embeddings
  (NLEmbedding) have no counterpart here. The closeness is on another scale, so a feed made here ranks a little
  differently from one made on a Mac.
- **The model** (`core/src/llm`, `AiEngine::plain_answer`, when it is downloaded): the Swift prompts, word for word,
  for the searches, the screening (score ≥ 7, journals you follow ≥ 5, near misses on a quiet day), the one-sentence
  summaries and the digest with its `foryou://` links. Without it: the paragraph's own phrases as searches, the
  ranking trusted ("Close to your interests (from …)"), and rows show the abstract's first sentences.
- **Desktop** (`desktop/src/foryou.ts`, `src-tauri/src/foryou.rs`): ✦ New for You in the sidebar with the count of
  new papers; the feed in the list (status and ↻, "In short", rows with Add / Add as Must Read, More Like This, Not for
  Me, Earlier), a find in the details (abstract, why it's here); ⚙ the settings (paragraph and Draft from My Library
  with the model, ORCID iD and people you publish with, the morning time, papers a day, preprints, what you follow); a
  library paper's menu follows its authors or papers citing it. Checked at start and every ten minutes; the run, the
  model's screening and summaries in the background. No system notification (no notification plugin): the count and
  a line in the status bar.
- **Android:** see the Android app below.
- Tests: `cargo test foryou` in `core` (Swift's files read and written, dates, due times, the prompts' answers read,
  digest links, ranking, whole runs on recorded OpenAlex and bioRxiv answers with and without a model, ORCID iD,
  feedback, two devices on one library, the notification). `LUNTA_FORYOU_DUMP=<dir> cargo test foryou::tests::dump_for_swift
  -- --ignored` writes a full foryou.json and watches.json for checking with the Apple apps' decoder.
